# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Service.API is a .NET 10 Web API (generic user-management service, formerly named "Escola") built as a layered ("Clean Architecture"-style) solution with 5 projects. It uses EF Core with SQL Server (`Microsoft.EntityFrameworkCore.SqlServer`), JWT bearer authentication, and BCrypt for password hashing.

## Commands

```bash
# Restore & build
dotnet build Service.slnx

# Run the API (from repo root or Service.API/)
dotnet run --project Service.API/Service.API.csproj

# EF Core migrations (DbContext and migrations assembly live in Service.Infra.Data)
dotnet ef migrations add <Name> --project Service.Infra.Data --startup-project Service.API
dotnet ef database update --project Service.Infra.Data --startup-project Service.API

# Run tests
dotnet test Service.Tests/Service.Tests.csproj
```

`appsettings.json` deliberately ships `ConnectionStrings:DefaultConnection` and `Jwt:SecretKey` empty. Real values for local dev live in `Service.API/.env` (gitignored; loaded via `DotNetEnv.Env.Load()` at the very top of `Program.cs`, before `WebApplication.CreateBuilder(args)`, so the values land in the process environment and are then picked up by ASP.NET Core's built-in environment-variables configuration provider). `Service.API/.env.example` is the committed template (`ConnectionStrings__DefaultConnection`, `Jwt__SecretKey` — double underscore = nested config key). Copy it to `.env` and fill in real values before running. The API needs a SQL Server instance reachable at that connection string before login/token generation will work. Same pattern for the ingestion pipeline: `Service.API/ingestion.config.json` is gitignored (per-deployment/per-client, not secret but not shared across deployments either) — copy the committed `Service.API/ingestion.config.json.example` to `ingestion.config.json` and point its CSV `path`s at real files before running the Robot (`POST /api/robot/run`). `Service.API/Imports/` (where the example config's CSV paths point by default) is also gitignored — it's a local drop folder, not a place to commit sample/test data.

### Key patterns

- **Generic base service/repository**: `BaseService<TEntity, TGetDTO, TPostDTO, TPutDTO>` and `BaseRepository<T>` implement CRUD + pagination once; entity-specific classes (`UserService`, `UserRepository`) extend them and only implement `ToGetDTO`/`ToEntity`/`ApplyUpdate` mapping plus any custom queries (e.g. `GetByEmail`). Follow this pattern when adding new entities rather than writing bespoke CRUD.
- **Soft delete**: `BaseEntity` has `deletedAt`/`deletedBy`; `BaseRepository` filters `deletedAt == null` on reads and sets `deletedAt` instead of removing rows on delete. Any new entity/query must respect this filter.
- **Audit fields are automatic, not passed as parameters**: `BaseRepository<T>` injects `ICurrentUserService` (`Service.Domain.Account`, implemented by `CurrentUserService` in `Service.Infra.Ioc` via `IHttpContextAccessor` + `ClaimsPrincipalExtension.GetUserId()`) and uses it to fill `createdBy`/`updatedBy`/`deletedBy` (alongside `createdAt`/`updatedAt`/`deletedAt` via `DateTime.UtcNow`) on every `AddAsync`/`UpdateAsync`/`DeleteAsync`. Neither `IBaseService` nor controllers pass a `userId` around — don't reintroduce that parameter when adding new entities/modules.
- **All `BaseEntity` audit columns are nullable** (`createdAt`/`updatedAt`/`deletedAt` as `DateTime?`, `createdBy`/`updatedBy`/`deletedBy` as `int?`) — never make them non-nullable again, even though the app always populates `createdAt`/`createdBy` on insert. `createdAt` also has a DB-level default (`HasDefaultValueSql("now()")`) as a safety net for any insert path that bypasses `BaseRepository`. Every `IEntityTypeConfiguration<T>` must call `builder.ConfigureAuditFields()` (`Service.Infra.Data/EntitiesConfiguration/AuditableEntityConfigurationExtensions.cs`) once, near the top of `Configure(...)`, instead of repeating that default per entity.
- **Email uniqueness is app-level only, by design**: there is no unique DB constraint on `User.Email` — `UserService.AddAsync` checks via `GetByEmail` before inserting. This is a deliberate decision, not an oversight; don't add a unique index/migration for it without checking first.
- **User ↔ Role**: one `Role` has many `User`; each `User` has exactly one `Role` via the required `IdRole` FK (`OnDelete(DeleteBehavior.Restrict)` in `UserConfiguration`), no default value and no seed data — the DB is treated as empty, so there's no backfill concern. `UserService.AddAsync`/`UpdateAsync` both validate `IdRole` via `IRoleRepository.Exists(...)` before touching the repository, throwing `BadRequestException("Role not found.")` — don't let an invalid `IdRole` reach the DB and surface as a raw FK-violation 500.
- **Forecast ↔ Product/Center**: `Forecast` has required `IdProduct`/`IdCenter` FKs (`OnDelete(DeleteBehavior.Restrict)` in `ForecastConfiguration`, unidirectional — no `ICollection<Forecast>` back-reference on `Product`/`Center`). `ForecastService.AddAsync` validates both FKs via `IProductRepository.Exists(...)`/`ICenterRepository.Exists(...)` before touching the repository, same `BadRequestException` pattern as `UserService`↔`Role`. This is the template for any future join-style entity with multiple FKs (e.g. the pending `CenterProduct` — see TODO.md, blocked on `Partner`/`Tags`/`Reasons` not existing yet).
- **`Forecast`/`History` are immutable except their quantity field**: `ForecastPutDto` only has `Quantity`, `HistoryPutDto` only has `Consumption` (renamed from `Quantity` 2026-09-14, "vamos em Histories renomear quantity para Consumption" — `History` is the only one of the two with this name; `Forecast.Quantity` is untouched, so don't rename it too) — `IdProduct`, `IdCenter`, and `Date` are set once on create and can't be changed via `PUT` on either. Don't add those fields back to a PUT DTO without an explicit request; if the product/center/date is wrong, the intended flow is delete + recreate, not edit-in-place. `History` is structurally identical to `Forecast` (same FKs, same immutable-except-quantity-field rule, just a different name for that field) — treat it as the reference pattern for any other "FK + FK + quantity + Date" fact-table-style module going forward. **Exception**: `History.DiscardStatus` (`Service.Domain.Enums.DiscardStatus`: `NotReviewed`/`Reviewed`/`Discarded`) breaks the "PUT is quantity-only" rule — it's a required field on `HistoryPutDto` alongside `Consumption` (breaking change to the old Quantity-only PUT payload), because unlike the FK/Date fields it represents a review workflow that's meant to change after creation (someone reviews historical consumption and flags outliers before they feed the Adu calculation). Every new `History` row defaults to `NotReviewed` (`HasDefaultValue` in `HistoryConfiguration`, plus the entity property's own C# default — covers both `HistoryService.ToEntity`, which hardcodes it, and `HistoryIngestionWriter`, which never sets it) and is absent from `HistoryPostDto` entirely; only `PUT` can move it to `Reviewed`/`Discarded`. `HistoryIngestionWriter`'s upsert path never touches `DiscardStatus` on update either, so re-syncing consumption data from a client feed doesn't clobber review work already done through the API. `ingestion.config.json`'s `History` source still maps a CSV column literally named `"Quantity"` — only the `target` changed, to `"Consumption"` (the CSV/source column name is the client's business key naming, not tied to our internal property name).
- **`Reason.IsFromSystem` is API-immutable**: it's never in `ReasonPostDto`/`ReasonPutDto` — `ReasonService.ToEntity` always sets it `false` on create. It can only become `true` via a direct DB update outside the API. When `true`, `ReasonService.ApplyUpdate` throws `HttpException(..., 403)` before any field changes, and the overridden `DeleteAsync` throws the same (403) before calling `base.DeleteAsync` — a system-seeded `Reason` can never be edited or deleted through the API. Follow this pattern (block in `ApplyUpdate`/override `DeleteAsync` with a pre-check) for any future "protected/system record" flag.
- **`CenterProduct` has 8 FKs, 2 required and 6 optional**: `IdProduct`/`IdCenter` required; `IdOriginCenter` (also → `Center`, a second FK to the same table — no inverse collection on `Center`, both configured `WithMany()`/`OnDelete(DeleteBehavior.Restrict)` to avoid ambiguity), `IdProvider` (→ `Partner`), `IdTag`, `IdReason`, `IdAllocationGroup`, `IdBufferProfile` (→ `BufferProfile` — a `CenterProduct` has zero or one buffer profile) are all nullable. `CenterProductService` validates every FK it accepts (`if (id.HasValue)` for the optional ones) via `ValidateOptionalForeignKeysAsync`, called from both `AddAsync` and `UpdateAsync` — the same "never let an invalid FK reach the DB as a raw 500" rule applies to optional FKs too, not just required ones. **`CenterProduct.Adu`** (`decimal?`, `HasPrecision(18,4)`) is the DDMRP calculated field the Robot's calculation pipeline writes — it's **read-only through the API**: present in `CenterProductGetDto` but absent from both `CenterProductPostDto`/`PutDto`, and neither `ToEntity` nor `ApplyUpdate` ever assigns it, so it can only change via a calculation step's own `UPDATE` (`CalculateAduStandardDesvAndCvStep`, a plain C# class — see the calculation-pipeline bullet below; same "system-writes-this, not the user" convention as `Reason.IsFromSystem`/`BufferAdjustmentFactor`'s `*Old` fields). `FutureAduDays`/`HistoryAduDays` (`int?`, both nullable, no default) are the per-item override of how many days forward/back the Adu calculation should use — unlike `Adu` these **are** normal editable fields (in both DTOs, set in `ToEntity`/`ApplyUpdate` like any other optional field). **`CenterProduct.Adi`** (`decimal?`, `HasPrecision(18,4)`, added 2026-09-12) follows the exact same read-only-via-API convention as `Adu` — present in `CenterProductGetDto` only, absent from `PostDto`/`PutDto`, untouched by `ToEntity`/`ApplyUpdate`; written by `CalculateAdiStep` (see the calculation-pipeline bullet below and `Formulas.md`) — an Average-Demand-Interval metric, independent of `Adu`/`HistoryAduDays`/`FutureAduDays`. **`CenterProduct.StandardDeviation`/`Cv`** (both `decimal?`, `HasPrecision(18,4)`, added 2026-09-12) are two more robot-only calculated fields, same read-only-via-API convention (`CenterProductGetDto` only, absent from `PostDto`/`PutDto`/`ToEntity`/`ApplyUpdate`) — written by `CalculateAduStandardDesvAndCvStep` itself (not a separate step: same `HistoryAduDays` window as Adu's Histórico, so no reason to re-read `History` twice), see the calculation-pipeline bullet below and `Formulas.md`. **`CenterProduct.UseSuggestedLTFactor`/`UseSuggestedVariabilityFactor`** (both `bool`, `HasDefaultValue(true)`, added 2026-09-13) are **normal user-editable fields**, unlike `Adu`/`Adi`/`StandardDeviation`/`Cv` — present in `PostDto`/`PutDto` (both default `true` at the C# level, same "optional with a stated default" treatment as `Order.IsFictional`) and set in `ToEntity`/`ApplyUpdate` like any other field. They toggle whether that `CenterProduct` should use the system-suggested Lead Time/Variability factor (presumably derived from its `BufferProfile.LeadTimeCategory`/`VariabilityCategory`) versus a manual override — no calculation step reads them yet as of this writing; wiring them into an actual factor calculation is future work. **`CenterProduct.RedZoneBase`/`RedZoneSafe`/`YellowZone`/`GreenZone`** (all `decimal?`, `HasPrecision(18,4)`, added 2026-09-13) are the DDMRP buffer zone sizes — same read-only-via-API convention as `Adu`/`Adi`/`StandardDeviation`/`Cv` (`CenterProductGetDto` only, absent from `PostDto`/`PutDto`/`ToEntity`/`ApplyUpdate`, "apenas o robô deve editar"). **`CenterProduct.RedZone` is *not* a physical column** — it's a computed read-only C# property (`RedZoneBase + RedZoneSafe`, nullable-lifted so it's `null` unless *both* are set, not `0`), explicitly `builder.Ignore(cp => cp.RedZone)`'d in `CenterProductConfiguration` so EF never tries to map it; a future zone-sizing step only ever needs to write `RedZoneBase`/`RedZoneSafe` (never `RedZone` directly — there's no setter, by design, since it must always equal their sum). Follow this "derived value = C# computed property + `Ignore()`, not a stored column kept in sync by hand" pattern for any other future field that's always a pure function of other columns. **No calculation step writes any of these yet** — they exist as reserved columns for a future zone-sizing step (would presumably read `Adu`/`BufferAdjustmentFactor`/`UseSuggestedLTFactor`/`UseSuggestedVariabilityFactor`/`UseDafOnGreenZone`), the same "add the column now, wire the step later" sequencing already used for `Adi` before `CalculateAdiStep` existed. **`CenterProduct.UseDafOnGreenZone`** (`bool`, `HasDefaultValue(false)`, added 2026-09-13) is another normal user-editable field, same treatment as `UseSuggestedLTFactor`/`UseSuggestedVariabilityFactor` (in `PostDto`/`PutDto`, set in `ToEntity`/`ApplyUpdate`) — toggles whether `DemandAdjustmentFactor` (DAF) applies to the green zone when the still-unbuilt zone-sizing step computes `RedZone`/`YellowZone`/`GreenZone`. Defaults `false` (DAF affecting only red/yellow, not green, is the more common DDMRP default) — confirmed explicitly, don't assume `true` like the other two `UseSuggested*` flags.
- **`CenterProduct.CustomLeadTimeFactor`/`CustomVariabilityFactor`** (both `decimal`, `HasPrecision(18,4)`, `HasDefaultValue(1)`, added 2026-09-13, briefly placed on `Product` and moved here the same day) are normal user-editable fields (in `PostDto`/`PutDto`, both default `1` at the C# level, set in `ToEntity`/`ApplyUpdate` like any other field) — the manual override values used when `UseSuggestedLTFactor`/`UseSuggestedVariabilityFactor` is `false` instead of `BufferProfile.LeadTimeFactor`/`VariabilityFactor`. Living on `CenterProduct` (not `Product`) matches the "suggested vs. custom" toggle's own scope (per product+center) and the `BufferProfile` value it substitutes for (also assigned per `CenterProduct`) — don't move it back to `Product`. No calculation step reads them yet, same "reserved for future wiring" status as `RedZoneBase`/`RedZoneSafe`/`YellowZone`/`GreenZone`. **`CenterProduct.GreenZoneParametrizationUseMoq`/`UseAduXFrequency`/`UseAduXLeadTimeXFactLeadTime`** (all `bool`, `HasDefaultValue(true)`, added 2026-09-13) are three more normal user-editable fields (`PostDto`/`PutDto`, `ToEntity`/`ApplyUpdate`) — per-`CenterProduct` toggles for whether each of the green-zone candidates (Moq / Adu×Frequency / Adu×LeadTime×LeadTimeFactor — the future zone-sizing step's `MAX(Verde1, Verde2, Verde3)`, see `Formulas.md`/the design discussion) participates in that `MAX`. Mirrors `BufferProfile`'s own `UseMoq`/`UseAdUxFrequency`/`UseAdUxDlTxFactorDlt` flags but scoped per product+center instead of per profile — not wired into a calculation step yet, same reserved status as the zone columns above. **`CenterProduct.BufferType`** (`Service.Domain.Enums.BufferType`, `HasDefaultValue(BufferType.Normal)`, added 2026-09-13, reused — not a new enum) is a normal user-editable field, same enum `BufferAdjustmentFactor.BufferType`/`BufferTypeOld` already use. Defaults to `Normal` at both DB and C# level, so — same "has a stated default → not `[Required]`" treatment as `Order.IsFictional` — it's only `[EnumDataType]` (still rejects an out-of-range value if one is sent) in `PostDto`/`PutDto`, not `[Required]`, and set in `ToEntity`/`ApplyUpdate` like any other field. **`CenterProduct.ZafRedZone`/`ZafYellowZone`/`ZafGreenZone`** (all `decimal`, `HasPrecision(18,4)`, `HasDefaultValue(0)`, `IsRequired()`, added 2026-09-13) are robot-only, same read-only-via-API convention as `RedZoneBase`/`RedZoneSafe`/`YellowZone`/`GreenZone` (`CenterProductGetDto` only, absent from `PostDto`/`PutDto`/`ToEntity`/`ApplyUpdate`) — the zone sizes after a `ZoneAdjustmentFactor` (ZAF) is applied on top of the base zones. Unlike the base zone columns (nullable, no DB default, reset to `0` by the calculation step before recomputing), these are non-nullable with a `0` DB default — same treatment as `Stock`/`PackQuantity`. No calculation step writes them yet. **`CenterProduct.QualifiedDemand`** (`decimal?`, `HasPrecision(18,4)`, added 2026-09-13) is robot-only, same read-only-via-API convention as `Adu`/`Adi` — present in `CenterProductGetDto` only, absent from `PostDto`/`PutDto`/`ToEntity`/`ApplyUpdate`, nullable with no DB default (unlike `Zaf*`, matches `Adu`/`Adi`/`RedZoneBase` instead). DB defaults: `SpikeHorizonValue` 60, `SpikeHorizonLTDays` 1, `SpikeThresholdAdu` 1, `SpikeThresholdPercentageRedZone` 0.5. Feeds the not-yet-implemented `CalculateQualifiedDemandStep` — see below and `Formulas.md`.

**`CenterProduct.QualifiedDemand` calculation (design confirmed 2026-09-13, not yet implemented as a step)**: sums, per `CenterProduct`, the "spike-qualified" pending outbound demand within a lead-time-driven horizon. Source data is every `Order` with `IsOutbound = 1` (fictional orders **are** included — no `IsFictional` filter, a deliberate correction from an earlier draft that excluded them), grouped by `(IdProduct, IdOriginCenter, DeliveryDate)` summing `Quantity - DeliveredQuantity` (pending quantity) per day. `IdOriginCenter` is matched to `CenterProduct.IdCenter` (the buffer being consumed by an outbound order lives at its origin center, not its destination). Only day-groups where `DeliveryDate > GETDATE()` (strictly future, excludes today and anything overdue) and `DeliveryDate <= GETDATE() + Horizon` count, where `Horizon` (days) is `CenterProduct.LeadTime * CenterProduct.SpikeHorizonLTDays` when `SpikeHorizonType = Dlt`, or `CenterProduct.SpikeHorizonValue` when `SpikeHorizonType = Days`. For each qualifying day-group, the day's pending-quantity sum counts in full if it clears a threshold — `>= CenterProduct.Adu * CenterProduct.SpikeThresholdAdu` when `SpikeThresholdType = Adu`, or `>= (RedZoneBase + RedZoneSafe) * CenterProduct.SpikeThresholdPercentageRedZone` when `SpikeThresholdType = PlanningRedZone` — otherwise that day contributes `0`. `CenterProduct.QualifiedDemand` is the **sum across all qualifying days** in the horizon (not per-day, not just the max day). No `BufferType` scoping — applies uniformly to every `CenterProduct` regardless of type — and no relation to MTO (`BufferProfile.IsMakeToOrder`), confirmed as an independent concept.

- **Ingestion pipeline ("Robot" — data-loading half)**: `POST /api/ingestion/run` (`[Authorize]`, optional `?view=` to run one source; omit to run every configured source) calls `IngestionService.RunAsync(view, ct)` directly; `RobotService` also calls it (always with `view: null`, as part of the composed run). It reads `Service.API/ingestion.config.json` (path from `Ingestion:ConfigPath` in `appsettings.json`) via `JsonIngestionConfigProvider`, which lists one `IngestionSourceConfig` per view (`View`, `Type`, `Path`, `FieldMappings`). Only `Type: "Csv"` is implemented (via `CsvIngestionSourceReader`, using CsvHelper) — API-based ingestion was explicitly deferred (2026-09-12) and would plug in as another `IIngestionSourceReader`/`IIngestionWriter` without touching existing code, since `IngestionService` picks readers/writers from the full injected `IEnumerable<T>` by `CanHandle(...)`. Each `FieldMappingConfig` is `{ Source?, Target, Default?, Lookup? }`: if `Source` is set, its raw CSV value is used when non-empty, else `Default`; if `Source` is omitted, the field is a hardcoded constant (`Default`) regardless of what the client sends (e.g. `Product.Segment` always `"BR"`). A `Lookup { Entity, By }` (currently `Product`/`Reference`, `Center`/`Code`, and `Partner`/`Code`) means the client CSV references rows by **business key**, not our internal `Id` — `IngestionService` batch-resolves all distinct values for each lookup field up front via `ILookupValueProvider`/`IProductRepository.GetIdsByReferencesAsync`/`ICenterRepository.GetIdsByCodesAsync`/`IPartnerRepository.GetIdsByCodesAsync` (one query per lookup field per run, not per row), and `FieldMappingEngine.MapRows` (pure, no I/O, in `Service.Application/Ingestion/`) resolves them per row, producing a row-level error (not aborting the whole file) when a reference/code doesn't resolve or is missing. Each view has its own `IIngestionWriter` (`Service.Infra.Data/Ingestion/Writers/`) that **upserts by natural/composite key** directly against `ApplicationDbContext` (bulk-fetch existing rows matching the batch's keys, then `AddRange`/mutate + one `SaveChangesAsync` — bypasses `BaseRepository`'s per-row save for import-volume performance): `Centers` by `Code`, `Products` by `Reference`, `CenterProducts` by `(IdProduct, IdCenter)`, `Forecast`/`History` by `(IdProduct, IdCenter, Date)`, `Orders` (any view with `"table": "Orders"`) by `(OrderNumber, IdDestinyCenter, IdOriginCenter, IdProduct)`. `CenterProductIngestionWriter` maps the FK pair plus `IdOriginCenter` and `IdProvider` (both optional — `Center`/`Code` and `Partner`/`Code` lookups respectively, `"required": false` since a row without one is still valid), `PackQuantity`/`Moq`/`LeadTime`/`Frequency`, and (insert-only) `HistoryAduDays`/`FutureAduDays`. **`Tag`/`Reason`/`AllocationGroup`/`BufferProfile` are deliberately *not* wired to ingestion** (2026-09-13, explicit decision) — unlike `Provider`, which a client's ERP feed can reasonably supply, these four are configured by internal users directly via the API after the row exists, never sent in a client CSV; don't add them to this writer without being told the source column mapping. **`IIngestionWriter` is dispatched by full `IngestionSourceConfig`, not just the view name** (`bool CanHandle(IngestionSourceConfig source)` / `WriteAsync(IngestionSourceConfig source, List<Dictionary<string,string?>> mappedRows, CancellationToken ct)`) — this exists specifically so a writer can key off `IngestionSourceConfig.Table` instead of `View`, which is what makes the next paragraph possible.

**`GenericTableIngestionWriter`** (`Service.Infra.Data/Ingestion/Writers/`, 2026-09-13, replacing an earlier `CenterProductFieldUpdateIngestionWriter` that hardcoded `CenterProducts`) is the **config-only, any-table upsert writer for tables with no special business rules** — registered once, and the end state the whole `Table`-dispatch mechanism was building toward: "eu apenas deveria informar para qual tabela isso deveria ir... isso deve ser configurado apenas alterando o json sem precisar alterar o código." `CanHandle(source)` is true when `source.Table` is both non-empty and on its explicit **`AllowedTables`** allow-list (today: only `CenterProducts` — see why `Orders` isn't below) *and* resolves to a real EF entity type. That allow-list is a deliberate, small exception to "pure JSON": without it, a misconfigured (or malicious) `ingestion.config.json` could target **any** table reachable from `ApplicationDbContext` — including `Users`/`Roles`/`RefreshTokens` — and bulk-write things like `User.Password` from a CSV. Adding a table to the allow-list (one line) is the *only* code change this writer's design ever requires again; a **new view on an already-allowed table is pure config** — e.g. the `Clients`/`Providers` example that prompted this design (both saving into `Partners`) needs zero C# once `"Partners"` is on the list. It deliberately does **not** guard specific fields (e.g. `CenterProduct.Adu`/`Adi`/`StandardDeviation`/`Cv`) the way the old `CenterProductFieldUpdateIngestionWriter.ProtectedFields` did — a conscious choice, since the calculation pipeline always reruns after ingestion in `RobotService` and unconditionally overwrites those columns anyway (see the reset-then-recompute convention below), so a config author accidentally mapping a CSV column onto a calculated field is harmless in practice, not worth a maintenance burden that (as `Adi`/`StandardDeviation`/`Cv` proved) reliably gets forgotten when a new calculated field is added.

Mechanically: entity type resolution is `_context.Model.GetEntityTypes()` matched by `IEntityType.GetTableName()` (not a hardcoded table→type map), so it always agrees with whatever each `IEntityTypeConfiguration<T>.ToTable(...)` actually says. Per-entity **updatable properties** are cached (`PropertyCache`, keyed by CLR `Type`, built once via reflection): writable, non-navigation (only `string`/`int`/`decimal`/`DateTime`/`bool`/enum — a `Product`/`Center`/`Partner`-typed navigation property is never in this set, same "map the FK id, not the object" rule as everywhere else), excluding `Id` and the six `BaseEntity` audit columns. Every declared `Key` field and every mapped `FieldMappingConfig.Target` must resolve to one of these properties or the whole run throws `NotSupportedException` up front (same boundary convention: caught by `IngestionService`, rethrown as `BadRequestException`). Matching existing rows is genuinely dynamic: since the business `Key` can be any combination of properties (not the table's actual PK), there's no way to build one static LINQ `Where` for every possible table, so the writer fetches **every active row of that table** (`deletedAt == null`, no candidate-id prefiltering) via a small reflection shim (`FetchExistingAsync` invokes a private generic `_context.Set<TEntity>()`-based method through `MethodInfo.MakeGenericMethod`, since `DbContext` has no non-generic LINQ-capable `Set` for safe async querying) and matches in memory by joining each row's `Key` field values into one string (`KeyPartSeparator`/`NullKeyPart`) — acceptable because every table on the allow-list is master/reference-shaped (small), the same assumption `DeleteNonSent`'s full-table scan already makes for `Centers`/`Products`. **`IngestionSourceConfig.AllowInsert`** (bool, default `true`) is what preserves `Stock`'s original "never create a half-populated `CenterProduct`" guarantee: `Stock`'s config sets `"allowInsert": false` explicitly; a row with no existing match is then a row-level error (`"...doesn't create new rows"`) instead of an insert, otherwise (default) a genuinely new entity is `Activator.CreateInstance`'d, has every mapped field set, and is added via the non-generic `DbContext.Add(object)`. **Per-row conversion errors never crash the batch**: for each row, every mapped field's raw value is converted *before* any property is set on the entity (a `List<(PropertyInfo, object?)>` built up first) — if any single field fails to convert (bad format, blank non-nullable value), the whole row is reported as one `IngestionWriteResult.Errors` entry and skipped, exactly like every other writer, rather than throwing mid-mutation (which would both crash the entire run *and* risk leaving a tracked entity partially modified for `SaveChangesAsync` to persist anyway) — a real bug caught and fixed 2026-09-13 shortly after the writer was first built, before it had ever been exercised with a genuinely malformed value.

**`Orders` is deliberately *not* on `GenericTableIngestionWriter`'s allow-list** — it has its own dedicated **`OrderIngestionWriter`** (`Service.Infra.Data/Ingestion/Writers/`, 2026-09-13), still `Table`-dispatched (`CanHandle(source) => source.Table == "Orders"`, so every `OrderType` view still shares one class purely via config — `ProductionOrder`, `PurchaseOrder`, `SaleOrder`, `Transfers` all exist today, each just a config block with its own `Key`/`Type`/`IsInbound`/`IsOutbound`, no per-view code) but hand-written rather than generic, because it needs business rules the generic engine must never have: **fictional Orders (`Order.IsFictional`) are completely invisible to ingestion** — never matched (so a real feed never updates a hand-created/simulated Order even if its natural key coincides — a new, real `Order` is inserted alongside it instead), and never deleted. And **delete-non-sent for Orders always runs, unconditionally ignoring `IngestionSourceConfig.DeleteNonSent`** (the only writer that does this): every run soft-deletes non-fictional, active Orders whose `Type` matches *what's actually present in that file* and whose key wasn't sent — scoped by `Type` specifically so that, e.g., running `Transfers` can never delete `ProductionOrder`/`PurchaseOrder`/`SaleOrder` rows just because they're absent from the transfers file. This is safe to leave always-on (unlike the opt-in `DeleteNonSent` used everywhere else) precisely because of that `Type` scoping plus the fictional exclusion — the blast radius is inherently limited to "other real orders of the same type," never the whole table. `ProductionOrder`'s `Center` column maps to `IdDestinyCenter`, not `IdOriginCenter` — confirmed via a clarifying question (a production order's `Center` is where the produced quantity lands), not assumed.

**A cautionary tale from the same day**: right after `GenericTableIngestionWriter` shipped, `Centers`/`Products`/`CenterProducts`/`Forecast`/`History` briefly all had a `"table"` key added to their `ingestion.config.json` entries (an attempt to move everything onto the new mechanism). This didn't work as hoped and was reverted: `Centers`/`Products`/`Forecasts`/`Histories` aren't on `AllowedTables`, so those runs would just fail loudly (`"Unsupported ingestion view"` — no writer matches, since their `View` no longer matched the bespoke writer either after an earlier, unrelated singular-renaming edit); `CenterProducts` **was** allow-listed, though, so that one *silently* started routing through the generic writer instead of `CenterProductIngestionWriter` — quietly losing the "`HistoryAduDays`/`FutureAduDays` only set on insert" protection, since the generic writer has no per-field "insert-only" concept. **Moving one of the 5 bespoke `View`-dispatched writers onto the generic mechanism is not just a `"table"` edit** — it needs an equivalent for every bit of bespoke behavior first (here, an insert-only-field concept in `FieldMappingConfig`), plus adding that table to `AllowedTables`. Don't do it opportunistically; treat it as its own deliberate task if it's ever wanted. **`FieldMappingConfig.Required`** (bool, default `true`) makes a `Lookup` field optional: when `false` and the row's source value is empty, the target is simply left out of the mapped row (e.g. `IdOriginCenter` when `OriginCenterCode` is blank) instead of failing the row — a *present but unresolvable* value is still always an error regardless of `Required`, only a *missing* one is forgiven. **`HistoryAduDays`/`FutureAduDays` are only set by `CenterProductIngestionWriter` on insert, never on update** — same reasoning as `History.DiscardStatus`: they're a create-time default (`ingestion.config.json`'s `CenterProducts` source maps them as constants, `{ "target": "HistoryAduDays", "default": "90" }`/`{ "target": "FutureAduDays", "default": "0" }`, no `source`), and re-syncing from CSV shouldn't overwrite a value the user tuned afterward via `PUT`. **Two `FieldMappingConfig` entries can share the same `Lookup { Entity, By }`** (e.g. `CenterCode`→`IdCenter` and `OriginCenterCode`→`IdOriginCenter`, both `Center`/`Code`) — `IngestionService.ResolveLookupsAsync` groups mappings by `(Entity, By)` and pools distinct values from *every* mapping's `Source` column in that group before calling `ILookupValueProvider` once per group (a per-mapping loop that resolved only the first mapping's values was a real bug here, fixed 2026-09-12 — a second field sharing a lookup used to silently fail to resolve values that weren't also present under the first field's column). **`IngestionSourceConfig.DeleteNonSent`** (bool, default `false`, per-source in `ingestion.config.json`) opts a view into "full sync" semantics: after upserting, any existing active row not present in the current file gets soft-deleted (`deletedAt`/`deletedBy`, same as everywhere else — never a hard delete). For `Centers`/`Products` this scans the whole table (`Code`/`Reference` not in the sent set) since master data is small; for `CenterProducts`/`Forecast`/`History` the deletion candidates are scoped to only the `(IdProduct, IdCenter)` pairs already fetched for the upsert step (reusing that query, not a second full-table scan) — so turning this on for `Forecast`/`History` only prunes rows for the products/centers actually present in that file, not the entire fact table. Each writer reads `source.DeleteNonSent` off the `IngestionSourceConfig` it's given; `IngestionWriteResult.Deleted`/`IngestionRunResultDto.RowsDeleted` report the count. Safety net: `IngestionService` only calls the writer when `validRows.Count > 0`, so a source file that reads empty (misconfigured path, wrong header) can't accidentally wipe a whole table — but a file that's merely *incomplete* (truncated, missing some legitimate rows) will still delete those as "not sent," so `DeleteNonSent` is inherently riskier for `Forecast`/`History` than for master data; it defaults to `false` and should stay opt-in per source. **`IngestionSourceConfig.Key`** (list of target field names, e.g. `["Code"]` for `Centers`, `["Reference"]` for `Products`, `["IdProduct", "IdCenter"]` for `CenterProducts`, `["IdProduct", "IdCenter", "Date"]` for `Forecast`/`History`) declares which mapped fields are that view's join/match key — the fields used to find the existing row on insert-or-update, and which are *never* overwritten once a row exists (each writer's update branch simply never assigns to them, by construction — the same "immutable after creation" convention as `CenterProduct.IdProduct`/`IdCenter` etc. elsewhere in this doc, just for the ingestion pipeline instead of the CRUD API). `Key` is validated by `IngestionService.ValidateKeyMappings` before a run touches the DB: every declared key field must have a `FieldMappingConfig` targeting it, and that mapping can't be a constant (`Source: null`) — a join key with a fixed value would collapse every row onto the same match, which is always a config mistake, not an intended default. Add a field to `Key` whenever a new view's business/natural key should be protected this way; besides that validation, the 5 bespoke `View`-dispatched writers and `OrderIngestionWriter` don't read `Key` themselves (each hardcodes its own matching logic in code, per the `Key` values listed above — keep the two in sync when either changes), but `GenericTableIngestionWriter` does read it directly (it's the only way it can match rows generically, per the mechanics described above, since — unlike every bespoke writer — it doesn't know the target table's shape ahead of time). `Key` is also read by `FieldMappingEngine.MapRows`: every row-level error it produces is prefixed with `[SourceColumn=value, ...]` built from `Key`'s target fields resolved back to their `FieldMappingConfig.Source` CSV column names (e.g. `[MaterialCode=UNKNOWN, CenterCode=C1]`), so a failing row is identified by the values an operator can actually search for in the source file — not a line/row number (tried and explicitly rejected 2026-09-12: "não precisa ser o número da linha apenas as colunas key para identificar"). **Cron/scheduled triggering was explicitly deferred** (2026-09-12, "não precisa criar o cron agora") — today the pipeline only runs on-demand via `POST /api/robot/run`; when it's added, per [[project_robot_ddmrp_design]] use a simple daily-time `BackgroundService` (config-driven "run at HH:mm"), not a full cron-expression library, unless told otherwise. The exception-boundary convention holds here too: `Infra.Data` readers/writers/config-provider throw plain BCL exceptions (`FileNotFoundException`, `NotSupportedException`) for I/O/config problems — `IngestionService` (Application layer) is what catches those and re-throws as `BadRequestException`, since `Infra.Data` has no reference to `Service.Application` (only `Service.Domain`, same as every repository) and `AppException` lives in Application.
- **Calculation pipeline ("Robot" — DDMRP pre-calc half)**: `POST /api/calculation/run` (`[Authorize]`, no partial-step option — always every step) calls `CalculationService.RunAsync(ct)` directly; `RobotService` also calls it, as the second half of the composed run. It reads `Service.API/calculation.config.json` (path from `Calculation:ConfigPath`) via `JsonCalculationConfigProvider`, a flat ordered list of `CalculationStepConfig { Name, Parameters: [{ Name, Value }] }`. **Calculation steps are plain C# classes, not SQL Server stored procedures** — this was tried first (a generic `EXEC dbo.[Name]` executor calling DB-persisted procedures) and explicitly rejected (2026-09-12, "não gosto da ideia de procedures") specifically because deploying/changing one meant an EF migration just to run `CREATE OR ALTER PROCEDURE`. Instead, each step is an `ICalculationStep` (`Service.Domain/Interfaces/ICalculationStep.cs`: `CanHandle(string name)` + `ExecuteAsync(CalculationStepConfig, ct)`) implemented in `Service.Infra.Data/Calculation/Steps/*.cs`, constructor-injected with `ApplicationDbContext` — same `CanHandle`-dispatch shape as `IIngestionWriter`, registered the same way (`IEnumerable<ICalculationStep>` in DI, `CalculationService` picks the one whose `CanHandle(stepConfig.Name)` matches, throwing `BadRequestException` up front if none does — mirrors ingestion's "no writer/reader matches" handling). A step is free to implement its logic however fits — LINQ, `ExecuteUpdateAsync`, or (like `CalculateAduStandardDesvAndCvStep`) a hand-written set-based SQL string run via `ApplicationDbContext.Database.ExecuteSqlRawAsync` when the logic doesn't translate cleanly through LINQ — but there is **no DB-persisted object and no migration needed to change one**; editing the C# file *is* the deployment. `CalculationService.RunAsync` executes steps **strictly in config order** and **stops at the first failing step** (unlike ingestion's per-row tolerance) — DDMRP calculations are assumed to be a dependency chain (a later step may read what an earlier one wrote), so continuing past a failure risks computing on wrong data; a step's own exception handling should catch its failure and return `CalculationStepResult { Success = false, Error }` rather than let it throw (see `CalculateAduStandardDesvAndCvStep`'s try/catch) — steps after a failure are simply never attempted (not represented in the result list at all). **`Service.Infra.Data/Calculation/Steps/*.cs`** is the centralized home for every calculation step (`CalculateAduStandardDesvAndCvStep.cs` was the first, registered in `CanHandle` as `"CalculateAduStandardDesvAndCv"`; `CalculateAdiStep.cs` is the second, `"CalculateAdi"`; `ApplyBafStep.cs` is the third, `"ApplyBAF"`; `CalculateNormalBufferZonesStep.cs` is the fourth, `"CalculateNormalBufferZones"`; `CalculateMinMaxBufferZonesStep.cs` is the fifth, `"CalculateMinMaxBufferZones"`; `CalculateDynamicMinMaxBufferZonesStep.cs` is the sixth, `"CalculateDynamicMinMaxBufferZones"`; `ApplyZafStep.cs` is the seventh, `"ApplyZAF"`; `CalculateQualifiedDemandStep.cs` is the eighth, `"CalculateQualifiedDemand"` — see the dedicated paragraphs below). **`Formulas.md`** (repo root) is the parallel centralized doc for the *business rule* each step implements — write or update the formula there before/alongside writing its step, not after. `calculation.config.json.example` now has all eight steps, in this exact order (dependency-driven — see below): `"CalculateAduStandardDesvAndCv"` (empty `parameters` — its day-count inputs live on `CenterProduct.HistoryAduDays`/`FutureAduDays`, not pipeline parameters), `"CalculateAdi"` (one parameter, `{ "name": "ThresholdDays", "value": "360" }`), `"ApplyBAF"` (empty `parameters` — must run before the zone-calc steps since it decides `CenterProduct.BufferType`), `"CalculateNormalBufferZones"` (empty `parameters`), `"CalculateMinMaxBufferZones"` (one parameter, `{ "name": "ThresholdDays", "value": "180" }` — a different default than `CalculateAdi`'s), `"CalculateDynamicMinMaxBufferZones"` (empty `parameters` — its day-count input is `CenterProduct.HistoryAduDays`, same column Adu uses, not a step parameter), `"ApplyZAF"` (empty `parameters`), `"CalculateQualifiedDemand"` (empty `parameters` — must run last, after `ApplyZAF`, since it reads the final post-ZAF `RedZoneBase`/`RedZoneSafe`) — **`CalculateAdi` is the first step whose input is a step-level config parameter rather than a per-`CenterProduct` column**: `CalculateAdiStep` reads `step.Parameters` for `"ThresholdDays"` (case-insensitive, defaults to `360` if the parameter is omitted; returns `CalculationStepResult{Success=false}` — not a thrown exception — if present but not a valid int) and applies that single threshold to every `CenterProduct` in one run, unlike Adu's per-item `HistoryAduDays`/`FutureAduDays`. It also uses `ExecuteSqlInterpolatedAsync` instead of `ExecuteSqlRawAsync` specifically because the SQL now has a runtime-variable piece (the threshold) that needs to be a real SQL parameter, not string-concatenated — `ExecuteSqlRawAsync` stays correct for `CalculateAduStandardDesvAndCvStep` since that step's SQL has no external input to parameterize. **`CalculateAduStandardDesvAndCvStep` also writes `CenterProduct.StandardDeviation`/`Cv`** (2026-09-12, "ambas as regras usam praticamente os mesmos dados que o cálculo de ADU, então vamos colocar no mesmo step") — same `HistoryAduDays`/`RankedHistory` window as Historico (population `STDEVP`/`AVG` over `ISNULL(Consumption, 0)`, `Cv = StandardDeviation / Average` with `Cv = 0` when the average is `0`), independent of `FutureAduDays`/Misto. **Every calculation step that writes calculated columns runs a reset `UPDATE ... SET <column> = 0` first, before the real computation** (2026-09-12, "antes de realizar o calculo voce deve rodar um update Zerando as colunas de todos os itens (isso serve para todas as colunas calculadas)") — `CalculateAduStandardDesvAndCvStep` zeroes `Adu`/`StandardDeviation`/`Cv`, `CalculateAdiStep` zeroes `Adi`, both as the first statement in their SQL batch; the real `UPDATE` immediately after already covers every active row unconditionally, so the reset doesn't change the final result today, but it's the standing convention for every calculated `CenterProduct` column going forward — add it when writing a new one, even if it looks redundant against the current query shape. **`ApplyBafStep`** (2026-09-13, `"ApplyBAF"` in config, no parameters) reconciles `CenterProduct.BufferType`/zones against `BufferAdjustmentFactor` (BAF) — runs *before* every zone-calc step, since it's what decides which `BufferType` each `CenterProduct` has that day, and the zone-calc steps filter by it. Three sequential passes, each matching `BufferAdjustmentFactor` to `CenterProduct` by `(IdProduct, IdCenter)`: **(1) revert** — every BAF with `EffectiveTo < now` and `AlreadyReverted = false` writes its `BufferTypeOld`/`BufferDdmrpRedSafeOld`/`RedBaseOld`/`YellowOld`/`GreenOld` back onto the matching `CenterProduct` (via `ISNULL(...,  current value)`, so a `null` `*Old` field — no `CenterProduct` existed when the BAF was created — leaves that specific field untouched rather than nulling it), then flips `AlreadyReverted = true` so it never reverts twice; **(2) apply** — every BAF that's active *and* currently in its effective window (`IsActive = true` and `EffectiveFrom <= now <= EffectiveTo`, both bounds inclusive) writes its `BufferType` onto the matching `CenterProduct`; **(3) manual zones** — of those same active/in-window BAFs, the ones with `BufferType = ManualFixed` also write `YellowZone`/`GreenZone` directly and split `BufferDdmrpRed` evenly into `RedZoneSafe`/`RedZoneBase` (`BufferDdmrpRed / 2` each) — this is the *only* place `ManualFixed` items get their zones, since no zone-calc step touches that `BufferType`. Reverting a `Normal`/`MinMax`/`DynamicMinMax` zone in pass (1) has no lasting effect if that item's zone-calc step also runs that day (full recompute overwrites it) — reverting is only durable for `ManualFixed`, which has no recompute step to undo it. Same "don't dedupe multiple matching BAFs, trust future overlap validation" stance as the DAF/ZAF lookups elsewhere — see `Formulas.md`. **`CalculateNormalBufferZonesStep`** (2026-09-13) computes `CenterProduct.RedZoneBase`/`RedZoneSafe`/`YellowZone`/`GreenZone` — see `Formulas.md` for the exact formula (Adjusted Adu via `DemandAdjustmentFactor`, Yellow, `MAX` of three green candidates gated by `GreenZoneParametrizationUse*`, RedSafe/RedBase via `LeadTimeFactor`/`VariabilityFactor`). **Scoped to `CenterProduct.BufferType = 0` (Normal) only** — both the reset `UPDATE` and the real computation filter on it, so `ManualFixed`/`MinMax`/`DynamicMinMax` items are never touched by this step (their zones come from elsewhere — `ManualFixed` from `ApplyBafStep`, above). **Depends on `CenterProduct.Adu` already being computed**, which is why it's registered/configured *after* `CalculateAduStandardDesvAndCv` — order in `calculation.config.json` matters for this reason (steps run strictly in config order, per above). Uses `ExecuteSqlRawAsync` (no external parameter to bind, unlike `CalculateAdiStep`'s `ThresholdDays`). **Does not yet handle MTO** (`BufferProfile.IsMakeToOrder` / the still-unbuilt `CenterProduct.IsMto` from the deferred `SetMto` step, see [[project_setmto_step_design]]) — tracked in `TODO.md`, don't treat this step as "done" for MTO items. **`CalculateMinMaxBufferZonesStep`** (2026-09-13, `"CalculateMinMaxBufferZones"` in config, one parameter `ThresholdDays` default `180`) is the `BufferType = 2` (MinMax) counterpart: `YellowZone`/`RedZoneSafe` are hardcoded `0`, `GreenZone` reuses the *exact same* formula as the Normal step (same `AdjustedAdu`/DAF lookup, same `GreenZoneParametrizationUse*` gating), and `RedZoneBase` is the single highest `History.Consumption` value (not a sum or average) in the last `ThresholdDays` days (excluding `Discarded` rows, same windowing convention as Adu/Adi) — see `Formulas.md`. Also doesn't handle MTO yet. **`CalculateDynamicMinMaxBufferZonesStep`** (2026-09-13, `"CalculateDynamicMinMaxBufferZones"` in config, no parameters — uses `CenterProduct.HistoryAduDays` directly) is the `BufferType = 3` (DynamicMinMax) counterpart, and the most complex step in the pipeline so far: it needs a **rolling-window maximum**, computed via a recursive-CTE calendar date spine (`OPTION (MAXRECURSION 0)` is required — the default 100-level cap is easy to exceed) plus a `CROSS APPLY` correlated subquery per spine day, because SQL Server's window-function frame (`ROWS BETWEEN N PRECEDING`) requires `N` to be a constant and here it's `MAX(LeadTime, Frequency)`, which varies per `CenterProduct`. Uses **no DAF** anywhere (plain `Adu`, unlike the Normal/MinMax steps — see the explicit callout in `Formulas.md`). `RedZoneSafe` is hardcoded `0`; `YellowZone`/`GreenZone`/`RedZoneBase` are all `0` when the rolling-window maximum (`MaiorAcumulado`) is `0`, otherwise `LeadTime * Adu` / `Moq` / `MaiorAcumulado - (LeadTime * Adu)` respectively — see `Formulas.md` for the full derivation, including a worked/validated example. Also doesn't handle MTO yet. **`ApplyZafStep`** (2026-09-13, `"ApplyZAF"` in config) layers a `ZoneAdjustmentFactor` (ZAF) on top — scoped to `BufferType <> 1` (every type except `ManualFixed`, which never gets a ZAF), and must run *after* all three zone-calculation steps since it reads the zones they wrote. `CenterProduct.ZafRedZone`/`ZafYellowZone`/`ZafGreenZone` (`decimal`, `HasDefaultValue(0)`, robot-only like the base zones) store **only the adjustment delta** (`0` when no active/vigente `ZoneAdjustmentFactor` matches that specific zone) — a deliberate choice confirmed 2026-09-13 to avoid double-counting the base zone, since the step then does `GreenZone += ZafGreenZone`/`YellowZone += ZafYellowZone`/`RedZoneBase += ZafRedZone` (the red delta lands on `RedZoneBase` specifically, not `RedZoneSafe` — explicit, not inferred). A `ZoneAdjustmentFactor` targets exactly one zone (`TargetZone`) per row, so up to 3 can be active simultaneously for the same item (one per zone) — same "trust the future overlap validation, don't dedupe in the step" stance as `ApplyZafStep`'s DAF counterpart in the zone-calc steps. See `Formulas.md` for the exact per-zone formula. **`CalculateQualifiedDemandStep`** (2026-09-13, `"CalculateQualifiedDemand"` in config, no parameters, must run **last** — after `ApplyZAF`, since it reads the final `RedZoneBase`/`RedZoneSafe`) writes `CenterProduct.QualifiedDemand` — the DDMRP spike-qualified pending demand within a lead-time-driven horizon. Source is every `Order` with `IsOutbound = 1` (no `BufferType` scoping and no relation to MTO — confirmed independent), grouped by `(IdProduct, IdOriginCenter, DeliveryDate)` — `IdOriginCenter` matched against `CenterProduct.IdCenter`, since the buffer an outbound order consumes lives at its origin center. "Today" is a special combined bucket (not just another day-group): non-fictional orders with `DeliveryDate <= today` (overdue + due today) plus fictional orders with `DeliveryDate = today` exactly — this asymmetry (fictional orders never carry over as "overdue") was an explicit correction after an earlier draft simply excluded today from the horizon window entirely. Future days (`DeliveryDate > today`) don't distinguish fictional/real at all — every `Order` counts. Only day-groups within the horizon (today always included; future days need `DeliveryDate <= today + Horizon`) are considered — `Horizon` (days) is `LeadTime * SpikeHorizonLTDays` when `SpikeHorizonType = Dlt`, or `SpikeHorizonValue` when `SpikeHorizonType = Days`. Each qualifying day-group's pending-quantity sum (`Quantity - DeliveredQuantity`, summed) counts in full only if it clears a threshold — `>= Adu * SpikeThresholdAdu` (`SpikeThresholdType = Adu`) or `>= (RedZoneBase + RedZoneSafe) * SpikeThresholdPercentageRedZone` (`SpikeThresholdType = PlanningRedZone`) — otherwise that day contributes `0`; `QualifiedDemand` is the **sum across all qualifying days**, not a single day's value. Same reset-then-recompute convention as every other calculated column (`QualifiedDemand = 0` first, unconditional, no `BufferType` filter). See `Formulas.md` for the full breakdown. **`POST /api/robot/run` (`RobotService`) is the composed, "real" Robot trigger**: it calls `IIngestionService.RunAsync(view: null, ct)` (every configured ingestion source) and only then `ICalculationService.RunAsync(ct)`, returning both result sets in one `RobotRunResultDto { Ingestion, Calculation }` — **the data load always runs first, by construction** (calculation is a second, sequential `await`, not parallel), and if ingestion throws, calculation is never invoked at all (the exception propagates before that line runs). **History**: `IngestionController`/`CalculationController` were briefly removed (2026-09-12, "a única rota exposta deve ser run") in favor of `/api/robot/run` alone, then restored the same day — both standalone routes exist again for testing/debugging one half of the pipeline in isolation, alongside `/api/robot/run` for the guaranteed load-then-calculate production path. When cron triggering is eventually added (see the deferred note above), it should call `IRobotService.RunAsync` (not re-implement the ordering), same as the HTTP route does.
- **Report module** (scaffolded 2026-09-14, restructured the same day) — a home for hand-written report queries, separate from ingestion/calculation (it's read-only, on-demand, and not part of the Robot's load-then-calculate pipeline). **Each report is a first-class, fully-layered feature, not a name-dispatched plugin** — a first draft used the `CanHandle`-dispatch shape shared with `ICalculationStep`/`IIngestionWriter` (one generic `POST /api/report/run` action, one `IReport` interface, implementations picked by name at runtime) and was explicitly rejected twice, 2026-09-14: first "não gostei da ideia de uma rota run deveria ser /api/report/inventoryBufferManagement" (killed the generic `run` action in favor of a per-report URL), then "ainda não gostei com essa rota 'generica', quero que cada report seja realmente um rota controller, uma função do service, e um metodo no repository, os reports são o coração do sistema" (killed the single `{name}`-parameterized action entirely). The `IReport`/`ReportRequest`/`ReportParameterConfig`/`ReportRunRequestDto` dispatch plumbing was deleted outright, not layered around — **reports now follow the exact same `Controller → Service → Repository` shape as every CRUD module in this codebase**, just without a backing `BaseEntity`/`BaseRepository<T>` (there's no single entity a report CRUDs) — same "bespoke, non-generic repository" precedent as `IRefreshTokenRepository` (see the `Service.Domain` bullet above). Adding a new report means adding **three** things, not one: (1) a method on `Service.Domain/Interfaces/IReportRepository.cs` + its implementation in `Service.Infra.Data/Repositories/ReportRepository.cs` (one class holding every report's query, constructor-injected with `ApplicationDbContext`, LINQ-only — see below), (2) a method on `Service.Application/Interfaces/IReportService.cs` + `Service.Application/Services/ReportService.cs` (today a thin one-line delegation per method straight to the repository — the layer exists for consistency and future business logic, not because it does anything non-trivial yet), and (3) a dedicated `[HttpGet("...")]` action on `Service.API/Controllers/ReportController.cs` calling that service method. No DI registration changes needed per new report beyond what's already wired for `IReportRepository`/`IReportService` themselves. **Route per report, not `{name}`**: `GET /api/report/inventoryBufferManagement` (`[Authorize]`) is `ReportController.InventoryBufferManagement`, a normal parameterless (for now) action — no generic `{name}` segment, no request DTO carrying a report name; a future report with real filter parameters would just take typed action parameters (`[FromQuery] DateTime startDate`, etc.), the same way any other GET endpoint in this codebase does, not a generic `Dictionary<string,string>`/`Name`+`Value` parameter bag. No `report.config.json` — there's nothing to configure per-deployment. Not part of `RobotService`/`POST /api/robot/run` — reports are pulled on demand by a caller, not pushed on a schedule. **Reports are built with EF Core LINQ, not raw SQL strings** (2026-09-14, explicit — the opposite convention from calculation steps, which favor hand-written `ExecuteSqlRawAsync`/`ExecuteSqlInterpolatedAsync` SQL when the logic doesn't translate cleanly through LINQ): `ReportRepository` queries `ApplicationDbContext` via LINQ (navigation-property access, `.Select()`) and projects straight into flat result rows. **Result rows are flat, never nested** — a report joining `Center`/`Product`/etc. pulls the fields it needs up to the top level of the row class with a disambiguating prefix (e.g. `CenterCode`, `ProductDescription`), not a nested `Center { Code, Description }` sub-object the way `CenterProductGetDto.Center`/`Product` nest full related-entity DTOs — deliberate departure from the CRUD `GetDto` convention specifically for reports, since a report row is meant to be one flat, tabular record (spreadsheet/grid-shaped). **Report result row classes live in `Service.Domain/Report/Results/*.cs`** (not `Service.Application/DTOs`) so `Infra.Data` (`ReportRepository`) can construct them directly without depending on Application — same placement precedent as `CalculationStepResult`/`IngestionWriteResult`, which also travel straight from Domain to the controller with no Application-layer DTO indirection; `IReportRepository`/`IReportService` both reference the same Domain row type directly (no separate repository-result-vs-service-result mapping step, since there's no transformation to do between the two layers today). **`GetInventoryBufferManagementAsync`** (the first report) returns `List<InventoryBufferManagementRow>` — one row per `CenterProduct` (`deletedAt IS NULL`, inner-joined to a non-deleted `Center`/`Product`), carrying every `CenterProduct` column unprefixed plus `Center`/`Product` columns with a `Center`/`Product` prefix (`CenterCode`, `ProductReference`, etc. — `ABC` was dropped from `Product` the same day, so it's correctly absent here too), `Provider`/`BufferProfile` columns (`ProviderCode`/`ProviderDescription`/`BufferProfileName`, `null` when the FK is unset or the related row is soft-deleted — both are optional FKs, left-join semantics via `!= null` checks in the LINQ projection) and four order-derived aggregates: `Entradas`/`Saidas` sum `Order.Quantity - Order.DeliveredQuantity` (pending quantity) over **every** non-deleted inbound/outbound `Order` matching **both** `IdProduct` and the relevant center (`IdDestinyCenter`/`IdOriginCenter` respectively) — fictional orders are included in these two totals, not excluded; `EntradasFicticias`/`SaidasFicticias` are the same sums with an added `IsFictional = true` filter (a subset of `Entradas`/`Saidas`, not a separate non-overlapping bucket). **Matching Order to CenterProduct by both `IdProduct` and center (not center alone) was a confirmed design choice** (2026-09-14, asked explicitly since the user's dictated spec only mentioned the center join) — matching by center alone would repeat the same order totals across every product stored at that center, which doesn't fit a per-product buffer report. Each aggregate is a correlated LINQ subquery (`_context.Order.Where(...).Sum(...)` inside the outer `Select`) rather than a `GroupJoin`, since each of the 4 aggregates has a different filter combination and EF Core translates this pattern to a correlated `SELECT SUM(...)` subquery per row cleanly. Covered by `Service.Tests/InfraData/ReportRepositoryTests.cs` (real `ApplicationDbContext` on the InMemory provider, same rationale as `OrderIngestionWriterTests`/`GenericTableIngestionWriterTests` — non-obvious join/aggregation logic worth verifying directly), which pins down that a decoy order for a different product or a different center, and a soft-deleted order, must never leak into the sums; `ReportServiceTests` just confirms the service's pass-through delegation.
- **Database provider is SQL Server** (`Microsoft.EntityFrameworkCore.SqlServer`, wired via `options.UseSqlServer(...)` in `Service.Infra.Ioc/DependencyInjection.cs`) — the project ran on PostgreSQL/Npgsql until 2026-09-12, when it was switched to SQL Server only (not dual-provider; there is no runtime provider switch). `AuditableEntityConfigurationExtensions.ConfigureAuditFields` uses `HasDefaultValueSql("GETUTCDATE()")` (was `now()` under Npgsql) for `createdAt`'s DB-level default. All prior EF migrations (generated against Npgsql) were deleted since their SQL isn't valid against SQL Server — the very next step after this switch is generating a fresh initial migration (`dotnet ef migrations add InitialCreate --project Service.Infra.Data --startup-project Service.API`) against a real SQL Server instance, per [[feedback-migrations]] the user runs this themselves. `Service.API/.env.example`'s `ConnectionStrings__DefaultConnection` now shows the SQL Server format (`Server=...;Database=...;User Id=...;Password=...;TrustServerCertificate=True;`) instead of the old Npgsql one. Watch for `DateTime.Kind` differences if this ever needs to move providers again: Npgsql required UTC-kind `DateTime`s for `timestamptz`, SQL Server's `datetime2` is lenient about `Kind` — don't rely on that leniency, keep populating audit/date fields with `DateTime.UtcNow` regardless of provider.
