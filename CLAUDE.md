# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Service.API is a .NET 10 Web API (generic user-management service, formerly named "Escola") built as a layered ("Clean Architecture"-style) solution with 5 projects. It uses EF Core with SQL Server (`Microsoft.EntityFrameworkCore.SqlServer`), JWT bearer authentication, and BCrypt for password hashing.

## Commands

```bash
# Restore & build
dotnet build Service.slnx

# Run the API (from repo root or Service.API/)
dotnet run --project Service.API/Service.API.csproj

# EF Core migrations (DbContext and migrations assembly live in Service.Infra.Data)
dotnet ef migrations add <Name> --project Service.Infra.Data --startup-project Service.API
dotnet ef database update --project Service.Infra.Data --startup-project Service.API

# Run tests
dotnet test Service.Tests/Service.Tests.csproj
```

`appsettings.json` deliberately ships `ConnectionStrings:DefaultConnection` and `Jwt:SecretKey` empty. Real values for local dev live in `Service.API/.env` (gitignored; loaded via `DotNetEnv.Env.Load()` at the very top of `Program.cs`, before `WebApplication.CreateBuilder(args)`, so the values land in the process environment and are then picked up by ASP.NET Core's built-in environment-variables configuration provider). `Service.API/.env.example` is the committed template (`ConnectionStrings__DefaultConnection`, `Jwt__SecretKey` — double underscore = nested config key). Copy it to `.env` and fill in real values before running. The API needs a SQL Server instance reachable at that connection string before login/token generation will work. Same pattern for the ingestion pipeline: `Service.API/ingestion.config.json` is gitignored (per-deployment/per-client, not secret but not shared across deployments either) — copy the committed `Service.API/ingestion.config.json.example` to `ingestion.config.json` and point its CSV `path`s at real files before running the Robot (`POST /api/robot/run`). `Service.API/Imports/` (where the example config's CSV paths point by default) is also gitignored — it's a local drop folder, not a place to commit sample/test data.

### Key patterns

- **Generic base service/repository**: `BaseService<TEntity, TGetDTO, TPostDTO, TPutDTO>` and `BaseRepository<T>` implement CRUD + pagination once; entity-specific classes (`UserService`, `UserRepository`) extend them and only implement `ToGetDTO`/`ToEntity`/`ApplyUpdate` mapping plus any custom queries (e.g. `GetByEmail`). Follow this pattern when adding new entities rather than writing bespoke CRUD.
- **Soft delete**: `BaseEntity` has `deletedAt`/`deletedBy`; `BaseRepository` filters `deletedAt == null` on reads and sets `deletedAt` instead of removing rows on delete. Any new entity/query must respect this filter.
- **Audit fields are automatic, not passed as parameters**: `BaseRepository<T>` injects `ICurrentUserService` (`Service.Domain.Account`, implemented by `CurrentUserService` in `Service.Infra.Ioc` via `IHttpContextAccessor` + `ClaimsPrincipalExtension.GetUserId()`) and uses it to fill `createdBy`/`updatedBy`/`deletedBy` (alongside `createdAt`/`updatedAt`/`deletedAt` via `DateTime.UtcNow`) on every `AddAsync`/`UpdateAsync`/`DeleteAsync`. Neither `IBaseService` nor controllers pass a `userId` around — don't reintroduce that parameter when adding new entities/modules.
- **All `BaseEntity` audit columns are nullable** (`createdAt`/`updatedAt`/`deletedAt` as `DateTime?`, `createdBy`/`updatedBy`/`deletedBy` as `int?`) — never make them non-nullable again, even though the app always populates `createdAt`/`createdBy` on insert. `createdAt` also has a DB-level default (`HasDefaultValueSql("now()")`) as a safety net for any insert path that bypasses `BaseRepository`. Every `IEntityTypeConfiguration<T>` must call `builder.ConfigureAuditFields()` (`Service.Infra.Data/EntitiesConfiguration/AuditableEntityConfigurationExtensions.cs`) once, near the top of `Configure(...)`, instead of repeating that default per entity.
- **Email uniqueness is app-level only, by design**: there is no unique DB constraint on `User.Email` — `UserService.AddAsync` checks via `GetByEmail` before inserting. This is a deliberate decision, not an oversight; don't add a unique index/migration for it without checking first.
- **User ↔ Role**: one `Role` has many `User`; each `User` has exactly one `Role` via the required `IdRole` FK (`OnDelete(DeleteBehavior.Restrict)` in `UserConfiguration`), no default value and no seed data — the DB is treated as empty, so there's no backfill concern. `UserService.AddAsync`/`UpdateAsync` both validate `IdRole` via `IRoleRepository.Exists(...)` before touching the repository, throwing `BadRequestException("Role not found.")` — don't let an invalid `IdRole` reach the DB and surface as a raw FK-violation 500.
- **Forecast ↔ Product/Center**: `Forecast` has required `IdProduct`/`IdCenter` FKs (`OnDelete(DeleteBehavior.Restrict)` in `ForecastConfiguration`, unidirectional — no `ICollection<Forecast>` back-reference on `Product`/`Center`). `ForecastService.AddAsync` validates both FKs via `IProductRepository.Exists(...)`/`ICenterRepository.Exists(...)` before touching the repository, same `BadRequestException` pattern as `UserService`↔`Role`. This is the template for any future join-style entity with multiple FKs (e.g. the pending `CenterProduct` — see TODO.md, blocked on `Partner`/`Tags`/`Reasons` not existing yet).
- **`Forecast`/`History` are immutable except `Quantity`**: both `ForecastPutDto` and `HistoryPutDto` only have `Quantity` — `IdProduct`, `IdCenter`, and `Date` are set once on create and can't be changed via `PUT`. Don't add those fields back to a PUT DTO without an explicit request; if the product/center/date is wrong, the intended flow is delete + recreate, not edit-in-place. `History` is structurally identical to `Forecast` (same FKs, same immutable-except-quantity rule) — treat it as the reference pattern for any other "FK + FK + Quantity + Date" fact-table-style module going forward. **Exception**: `History.DiscardStatus` (`Service.Domain.Enums.DiscardStatus`: `NotReviewed`/`Reviewed`/`Discarded`) breaks the "PUT is Quantity-only" rule — it's a required field on `HistoryPutDto` alongside `Quantity` (breaking change to the old Quantity-only PUT payload), because unlike the FK/Date fields it represents a review workflow that's meant to change after creation (someone reviews historical consumption and flags outliers before they feed the Adu calculation). Every new `History` row defaults to `NotReviewed` (`HasDefaultValue` in `HistoryConfiguration`, plus the entity property's own C# default — covers both `HistoryService.ToEntity`, which hardcodes it, and `HistoryIngestionWriter`, which never sets it) and is absent from `HistoryPostDto` entirely; only `PUT` can move it to `Reviewed`/`Discarded`. `HistoryIngestionWriter`'s upsert path never touches `DiscardStatus` on update either, so re-syncing consumption data from a client feed doesn't clobber review work already done through the API.
- **`Reason.IsFromSystem` is API-immutable**: it's never in `ReasonPostDto`/`ReasonPutDto` — `ReasonService.ToEntity` always sets it `false` on create. It can only become `true` via a direct DB update outside the API. When `true`, `ReasonService.ApplyUpdate` throws `HttpException(..., 403)` before any field changes, and the overridden `DeleteAsync` throws the same (403) before calling `base.DeleteAsync` — a system-seeded `Reason` can never be edited or deleted through the API. Follow this pattern (block in `ApplyUpdate`/override `DeleteAsync` with a pre-check) for any future "protected/system record" flag.
- **`CenterProduct` has 8 FKs, 2 required and 6 optional**: `IdProduct`/`IdCenter` required; `IdOriginCenter` (also → `Center`, a second FK to the same table — no inverse collection on `Center`, both configured `WithMany()`/`OnDelete(DeleteBehavior.Restrict)` to avoid ambiguity), `IdProvider` (→ `Partner`), `IdTag`, `IdReason`, `IdAllocationGroup`, `IdBufferProfile` (→ `BufferProfile` — a `CenterProduct` has zero or one buffer profile) are all nullable. `CenterProductService` validates every FK it accepts (`if (id.HasValue)` for the optional ones) via `ValidateOptionalForeignKeysAsync`, called from both `AddAsync` and `UpdateAsync` — the same "never let an invalid FK reach the DB as a raw 500" rule applies to optional FKs too, not just required ones. **`CenterProduct.Adu`** (`decimal?`, `HasPrecision(18,4)`) is the DDMRP calculated field the Robot's calculation pipeline writes — it's **read-only through the API**: present in `CenterProductGetDto` but absent from both `CenterProductPostDto`/`PutDto`, and neither `ToEntity` nor `ApplyUpdate` ever assigns it, so it can only change via a calculation step's own `UPDATE` (`CalculateAduStep`, a plain C# class — see the calculation-pipeline bullet below; same "system-writes-this, not the user" convention as `Reason.IsFromSystem`/`BufferAdjustmentFactor`'s `*Old` fields). `FutureAduDays`/`HistoryAduDays` (`int?`, both nullable, no default) are the per-item override of how many days forward/back the Adu calculation should use — unlike `Adu` these **are** normal editable fields (in both DTOs, set in `ToEntity`/`ApplyUpdate` like any other optional field). **`CenterProduct.Adi`** (`decimal?`, `HasPrecision(18,4)`, added 2026-09-12) follows the exact same read-only-via-API convention as `Adu` — present in `CenterProductGetDto` only, absent from `PostDto`/`PutDto`, untouched by `ToEntity`/`ApplyUpdate`; written by `CalculateAdiStep` (see the calculation-pipeline bullet below and `Formulas.md`) — an Average-Demand-Interval metric, independent of `Adu`/`HistoryAduDays`/`FutureAduDays`. **`CenterProduct.StandardDeviation`/`Cv`** (both `decimal?`, `HasPrecision(18,4)`, added 2026-09-12) are two more robot-only calculated fields, same read-only-via-API convention (`CenterProductGetDto` only, absent from `PostDto`/`PutDto`/`ToEntity`/`ApplyUpdate`) — written by `CalculateAduStep` itself (not a separate step: same `HistoryAduDays` window as Adu's Histórico, so no reason to re-read `History` twice), see the calculation-pipeline bullet below and `Formulas.md`.
- **`IdProduct`/`IdCenter` are immutable after creation on every module that has both**: `CenterProduct`, `ZoneAdjustmentFactor`, `BufferAdjustmentFactor`, and `DemandAdjustmentFactor` all exclude these two fields from their `PutDto` entirely (unlike `Forecast`/`History`, every *other* field — including `CenterProduct`'s other 5 FKs — stays editable). `ApplyUpdate` never touches them and `UpdateAsync` doesn't validate them (they were already valid at creation and can't change) — only `AddAsync` validates them. To "fix" a wrong product/center on any of these, delete and recreate the record. Treat this as the default going forward for any new module shaped like these unless told otherwise.
- **`MasterBuffer` has 4 required FKs, two pairs pointing at the same tables**: `IdProduct`/`IdProductFather` both → `Product`; `IdCenter`/`IdCenterFather` both → `Center`. Same technique as `CenterProduct.IdOriginCenter`: separate navigation properties (`Product`/`ProductFather`, `Center`/`CenterFather`), each `WithMany()` with no inverse collection and `OnDelete(DeleteBehavior.Restrict)`. All 4 are validated only in `AddAsync` (all required).
- **`MasterBuffer.Sequency` is the only field editable via `PUT`**: `MasterBufferPutDto` has just `Sequency` — the 4 FKs are fixed at creation (mirrors the `Forecast`/`History`/`CenterProduct.IdProduct`/`IdCenter` immutable-FK precedent). `UpdateAsync` isn't even overridden (no FK validation needed since none can change); `ApplyUpdate` only touches `Sequency`.
- **Enum fields are real C# enums**, not raw ints: `Service.Domain.Enums.TargetZone` (`RedZone`/`YellowZone`/`GreenZone`), `Service.Domain.Enums.AdjustmentType` (`FlatValue`/`Percentage`), `Service.Domain.Enums.BufferType` (`Normal`/`ManualFixed`/`MinMax`/`DynamicMinMax`). EF Core stores them as `int` by convention (no `HasConversion` needed — matches each spec's `int` column type); DTOs use `[EnumDataType(typeof(...))]` to reject out-of-range values instead of silently accepting them. Follow this pattern (`Service.Domain.Enums`, plain `int`-backed enum, `[EnumDataType]` on the DTOs) for any future field described as "must be an enum with options X/Y/Z".
- **Enums serialize as their string name in JSON, not the underlying int**: `Program.cs` registers a global `JsonStringEnumConverter` via `AddControllers().AddJsonOptions(...)`. This means every enum field (`TargetZone`, `AdjustmentType`, `BufferType`, and any future one) is returned as e.g. `"RedZone"` in responses, and `POST`/`PUT` bodies accept the string name (not the number) — the DB column stays a plain `int`, only the JSON wire format changed. Don't add a per-DTO `[JsonConverter]` for this; it's already global.
- **`Note.CreatedByUser` is a real navigation to `User` via the inherited `createdBy` audit field** — the only entity in the project where an audit column (`createdBy`, normally just an `int?` set by `BaseRepository`) also has an EF relationship configured (`NoteConfiguration`: `HasOne(n => n.CreatedByUser).WithMany().HasForeignKey(n => n.createdBy)`). This is deliberate and scoped to `Note` only — don't add this navigation to `BaseEntity`/other entities' `createdBy` unless asked, it's not a generic pattern.
- **`Note` can only be edited by the user who created it**: `NoteService.ApplyUpdate` compares `entity.createdBy` (set automatically at creation, never touched again) against `ICurrentUserService.UserId` and throws `HttpException(..., 403)` before applying any change — same "check inside `ApplyUpdate`" technique as `Reason.IsFromSystem`. `NotePutDto` only has `Content` — `CenterProductId` is fixed at creation (same immutable-FK convention as other single-FK modules). **Delete is not restricted to the creator** — only edit was requested; if the same restriction should apply to `DeleteAsync`, that needs to be added explicitly (override `DeleteAsync` with the same `createdBy` check before calling `base.DeleteAsync`).
- **`BufferProfile` has no FKs at all** — a standalone configuration entity (no `Product`/`Center` relation), every field required, full-edit `PUT` (no immutable fields, since there's no FK to protect). It carries 5 dedicated enums (`SupplyType`, `LeadTimeCategory`, `VariabilityCategory`, `SpikeHorizonType`, `SpikeThresholdType`) — none of them reused across other modules, unlike `AdjustmentType`. `ProfileName` is intentionally short (`MaxLength(5)`) per spec, not a typo.
- **`DemandAdjustmentFactor` reuses `Service.Domain.Enums.AdjustmentType`** (`FlatValue`/`Percentage`) rather than a separate enum — when a new module's spec asks for an "AdjustmentType" enum with different casing/naming (e.g. "Flat" instead of "FlatValue"), check for an existing enum with that exact type name first; two enums can't share a name in `Service.Domain.Enums`, and reusing keeps modules consistent. If the requested values are genuinely different from an existing enum's, ask before either renaming the shared one (which affects every consumer) or introducing a same-concept-different-name duplicate.
- **`PATCH {id}/active` toggles `IsActive` on `BufferAdjustmentFactor`, `ZoneAdjustmentFactor`, `DemandAdjustmentFactor`, and `BufferProfile`**: body is `Service.Application/DTOs/Common/SetActiveDto.cs` (`{ "isActive": bool }`, shared across all of them — no per-module duplicate). Each `I<Entity>Service` declares `SetActiveAsync(int id, bool isActive, ...)`, implemented by fetching the entity, setting only `IsActive`, and calling `_repository.UpdateAsync(...)` directly — it bypasses `ApplyUpdate`/the full `PutDto` entirely, so it can't touch any other field by accident. This is the pattern for any future single-field "toggle" endpoint: a shared common DTO if the field/shape repeats, a dedicated service method, `PATCH {id}/<field>` on the controller — not a full `PUT`.
- **`BufferAdjustmentFactor`'s `*Old` fields (`BufferTypeOld`, `BufferDdmrpRedOld`/`YellowOld`/`GreenOld`) are always `null` for now**: none of them appear in `BufferAdjustmentFactorPostDto`/`PutDto` — `ToEntity` hardcodes them to `null` on create, and `ApplyUpdate` never touches them (so they stay `null` — nothing else can set them yet). This is intentional per explicit instruction ("os campos old sempre recebem null por enquanto"), not an oversight; don't wire them up to real values without being told the actual snapshot-on-change logic to implement. `BufferAdjustmentFactor.IdProduct`/`IdCenter` are also immutable after creation (excluded from the PUT DTO), same pattern as `CenterProduct`/`MasterBuffer`.
- **GET responses eager-load direct FK relations**: `BaseRepository<T>` exposes a `protected virtual IQueryable<T> ApplyIncludes(IQueryable<T> query) => query` hook used by both `GetByIdAsync` and `GetAllAsync`. Repositories with FK navigation properties override it (`UserRepository` → `.Include(u => u.Role)`; `ForecastRepository`/`HistoryRepository` → `.Include(x => x.Product).Include(x => x.Center)`) so the corresponding `GetDto` (`UserGetDto.Role`, `ForecastGetDto`/`HistoryGetDto`'s `Product`/`Center`) comes back populated instead of just the raw FK id. `Service.Application/Mappers/EntityMappingExtensions.cs` has the single `ToGetDto()` extension per entity (`Role`, `Center`, `Product`) reused both by that entity's own service and by every other service that nests it — when adding a field to `Product`/`Center`/`Role`, update the mapper once, not every place that embeds it. When adding a new module with a required FK, follow this pattern (override `ApplyIncludes`, add a nullable nested `XGetDto` property, map it via `entity.X?.ToGetDto()`) rather than leaving the relation as a bare id.
- **Auth**: JWT claims carry `"id"` and `"email"` (see `AuthenticateProvider.GenerateToken`); `ClaimsPrincipalExtension.GetUserId()` is the standard way to read the current user's id in controllers (see `UserController.UpdateUser`, which updates the authenticated caller rather than taking an id in the route). Passwords are hashed with `BCrypt.Net.BCrypt`.
- **Refresh tokens**: `POST /api/user/login` returns an `AuthResponseDto` (`id`, `name`, `email`, `accessToken`, `accessTokenExpiresAt`, `refreshToken`, `refreshTokenExpiresAt`) — not the old `{ Name, Token }` shape. `Service.Domain.Entities.RefreshToken` is a standalone table (not a `BaseEntity`/`IBaseRepository` resource — it's an auth artifact with its own `IRefreshTokenRepository`, no generic CRUD/controller), storing an opaque 64-byte random token (`IAuthenticate.GenerateRefreshToken()`) plus `ExpiresAt`/`RevokedAt`/`ReplacedByToken`. `POST /api/user/refresh-token` (no `[Authorize]` — the access token is expected to already be expired) exchanges an active refresh token for a new access+refresh pair and **rotates**: the old refresh token is marked revoked with `ReplacedByToken` pointing at the new one, it can't be reused. `POST /api/user/revoke-token` (`[Authorize]`) is the logout path — `AuthenticateService.RevokeTokenAsync` checks the token's `UserId` matches the caller's id (via `User.GetUserId()`) before revoking, so one user can't revoke another's session. `IAuthenticate` also exposes `GetTokenExpiration()`/`GetRefreshTokenExpiration()`, reading `Jwt:AccessTokenExpirationMinutes` (60) / `Jwt:RefreshTokenExpirationDays` (7) from `appsettings.json` (not secrets — same non-`.env` treatment as `Cors:AllowedOrigins`) — don't hardcode these durations elsewhere.
- **User creation is intentionally not public**: `POST /api/user` requires `[Authorize]` by design — there is no public self-signup endpoint; only an already-authenticated user can create another user. Do not remove that `[Authorize]` to "fix" onboarding.
- **Every HTTP response is an `ApiResponseDto<T>`** (`Success`, `Data`, `Errors`, `Timestamp`). Controller actions never construct it themselves — just `return Ok(data)`/`return NotFound()` etc. with the raw payload; the globally-registered `ApiResponseWrapperFilter` (an `IAsyncResultFilter`, added via `AddControllers(options => options.Filters.Add<ApiResponseWrapperFilter>())` in `Program.cs`) wraps every successful `ObjectResult`/`StatusCodeResult` into the envelope automatically. This was a deliberate choice over wrapping manually per-action specifically so it scales as more controllers/endpoints are added — never revert to manual per-action wrapping.
- **Error handling**: throw exceptions derived from `AppException` (`Service.Application.Exceptions`) — `NotFoundException` (404), `BadRequestException` (400), or the generic `HttpException(message, statusCode)` for an ad-hoc code — the exception itself carries the status code via its `StatusCode` property. `ExceptionMiddleware` is the single catch point: it reads `AppException.StatusCode` (falls back to 401 for `UnauthorizedAccessException`, 500 otherwise) and returns `ApiResponseDto<object?>.Fail(...)`. In production, an unexpected (non-`AppException`) error's message is hidden behind "Internal server error"; `AppException` messages are always shown (they're meant to be user-facing).
- **Pagination**: list endpoints take `PaginationParams` (`PageNumber`/`PageSize`) and return `PagedList<T>`; controllers call `Response.AddPaginationHeader(...)` to expose a `Pagination` response header (also exposed via CORS `Access-Control-Expose-Headers`).
- **CORS**: allowed origins come from `Cors:AllowedOrigins` in `appsettings.json` (a plain string array, not a secret — don't move it to `.env`), read once in `Program.cs` into an `AddCors` policy named `"Default"` applied via `app.UseCors("Default")`. Defaults to an empty array (blocks all cross-origin requests) until a real frontend origin is added.
- **Health checks**: `GET /health/live` (liveness — always returns `Healthy`, checks nothing, no dependencies) and `GET /health/ready` (readiness — runs checks tagged `"ready"`) are wired in `Program.cs` via the built-in `Microsoft.Extensions.Diagnostics.HealthChecks` (no NuGet package needed — it ships with the `Microsoft.NET.Sdk.Web` shared framework that `Service.API` already targets). `Service.API/HealthChecks/DatabaseHealthCheck.cs` is the only check registered so far (tagged `"ready"`), and calls `ApplicationDbContext.Database.CanConnectAsync()` — add new checks the same way (implement `IHealthCheck`, register with `AddCheck<T>(name, tags: ["ready"])`) rather than writing ad-hoc ping endpoints. These endpoints bypass MVC entirely (no `[Authorize]`, no `ApiResponseDto<T>` envelope — orchestrators expect a plain 200/503) and return the framework's default plain-text body; don't route them through `ApiResponseWrapperFilter`.
- **Ingestion pipeline ("Robot" — data-loading half)**: `POST /api/ingestion/run` (`[Authorize]`, optional `?view=` to run one source; omit to run every configured source) calls `IngestionService.RunAsync(view, ct)` directly; `RobotService` also calls it (always with `view: null`, as part of the composed run). It reads `Service.API/ingestion.config.json` (path from `Ingestion:ConfigPath` in `appsettings.json`) via `JsonIngestionConfigProvider`, which lists one `IngestionSourceConfig` per view (`View`, `Type`, `Path`, `FieldMappings`). Only `Type: "Csv"` is implemented (via `CsvIngestionSourceReader`, using CsvHelper) — API-based ingestion was explicitly deferred (2026-09-12) and would plug in as another `IIngestionSourceReader`/`IIngestionWriter` without touching existing code, since `IngestionService` picks readers/writers from the full injected `IEnumerable<T>` by `CanHandle(...)`. Each `FieldMappingConfig` is `{ Source?, Target, Default?, Lookup? }`: if `Source` is set, its raw CSV value is used when non-empty, else `Default`; if `Source` is omitted, the field is a hardcoded constant (`Default`) regardless of what the client sends (e.g. `Product.Segment` always `"BR"`). A `Lookup { Entity, By }` (currently `Product`/`Reference` and `Center`/`Code`) means the client CSV references rows by **business key**, not our internal `Id` — `IngestionService` batch-resolves all distinct values for each lookup field up front via `ILookupValueProvider`/`IProductRepository.GetIdsByReferencesAsync`/`ICenterRepository.GetIdsByCodesAsync` (one query per lookup field per run, not per row), and `FieldMappingEngine.MapRows` (pure, no I/O, in `Service.Application/Ingestion/`) resolves them per row, producing a row-level error (not aborting the whole file) when a reference/code doesn't resolve or is missing. Each view has its own `IIngestionWriter` (`Service.Infra.Data/Ingestion/Writers/`) that **upserts by natural/composite key** directly against `ApplicationDbContext` (bulk-fetch existing rows matching the batch's keys, then `AddRange`/mutate + one `SaveChangesAsync` — bypasses `BaseRepository`'s per-row save for import-volume performance): `Centers` by `Code`, `Products` by `Reference`, `CenterProducts` by `(IdProduct, IdCenter)`, `Forecast`/`History` by `(IdProduct, IdCenter, Date)`. `CenterProductIngestionWriter` maps the FK pair plus `IdOriginCenter` (optional, its own `Center`/`Code` lookup), `PackQuantity`/`Moq`/`LeadTime`/`Frequency`, and (insert-only) `HistoryAduDays`/`FutureAduDays` — the remaining "internal" optional FKs on `CenterProduct` (`Provider`/`Tag`/`Reason`/`AllocationGroup`/`BufferProfile`) still aren't wired to ingestion, since those are set by internal users via the API, not typically sent by a client ERP feed; extend that writer if a client needs to send them. **`IIngestionWriter` is dispatched by full `IngestionSourceConfig`, not just the view name** (`bool CanHandle(IngestionSourceConfig source)` / `WriteAsync(IngestionSourceConfig source, List<Dictionary<string,string?>> mappedRows, CancellationToken ct)`) — this exists specifically so a writer can key off `IngestionSourceConfig.Table` instead of `View`, which is what makes the next paragraph possible. **`IngestionSourceConfig.Table`** (string, optional) lets a view target an *existing* entity table for a **partial, update-only field sync** without writing a dedicated `IIngestionWriter` class per view (2026-09-12, rejected the earlier per-view `StockIngestionWriter` approach specifically because "haverão outras views que atualizam campos de centerProducts" — more such views were expected): `CenterProductFieldUpdateIngestionWriter` (`Service.Infra.Data/Ingestion/Writers/`) is registered once and `CanHandle`s **any** view whose config sets `"table": "CenterProducts"` (the view's own `View`/name is irrelevant to dispatch — `Stock` is just the first such view, `key` must be exactly `["IdProduct","IdCenter"]`). It **never inserts** — a row whose `(IdProduct, IdCenter)` doesn't already exist is a row-level error (`"no CenterProduct found for..."`), because a partial-field feed (e.g. just a stock quantity) doesn't carry the other required columns (`PackQuantity`/`Moq`/etc.) a brand-new `CenterProduct` would need — only the full `CenterProducts` view (still its own bespoke `CenterProductIngestionWriter`, matched by `View` as before, since `Table` is left unset there) creates rows. Which `CenterProduct` property each mapped field updates is driven entirely by `FieldMappingConfig.Target` (e.g. `Stock`'s `ingestion.config.json` maps `Quantity`→`Stock`) resolved via reflection against a fixed allow-list (`CenterProductFieldUpdateIngestionWriter.UpdatableProperties`: writable, non-navigation, non-audit properties, built once via `typeof(CenterProduct).GetProperties()`) — `Id`/`IdProduct`/`IdCenter`/the audit columns/**`Adu`** (system-calculated, same read-only-via-ingestion rule as read-only-via-API) are explicitly excluded, and mapping to any other unknown/excluded name throws `NotSupportedException` (caught by `IngestionService` and rethrown as `BadRequestException`, same boundary convention as reader/lookup errors). To add another such view later (for a *different* field, still on `CenterProducts`), it's config-only: a new view block with `"table": "CenterProducts"` and whatever `FieldMappingConfig`s you need — no new C# writer. A future table needing this same "many views, partial updates, no insert" pattern would get its own sibling writer (same shape, different `CanHandle`/allow-list), not a change to this one. **`FieldMappingConfig.Required`** (bool, default `true`) makes a `Lookup` field optional: when `false` and the row's source value is empty, the target is simply left out of the mapped row (e.g. `IdOriginCenter` when `OriginCenterCode` is blank) instead of failing the row — a *present but unresolvable* value is still always an error regardless of `Required`, only a *missing* one is forgiven. **`HistoryAduDays`/`FutureAduDays` are only set by `CenterProductIngestionWriter` on insert, never on update** — same reasoning as `History.DiscardStatus`: they're a create-time default (`ingestion.config.json`'s `CenterProducts` source maps them as constants, `{ "target": "HistoryAduDays", "default": "90" }`/`{ "target": "FutureAduDays", "default": "0" }`, no `source`), and re-syncing from CSV shouldn't overwrite a value the user tuned afterward via `PUT`. **Two `FieldMappingConfig` entries can share the same `Lookup { Entity, By }`** (e.g. `CenterCode`→`IdCenter` and `OriginCenterCode`→`IdOriginCenter`, both `Center`/`Code`) — `IngestionService.ResolveLookupsAsync` groups mappings by `(Entity, By)` and pools distinct values from *every* mapping's `Source` column in that group before calling `ILookupValueProvider` once per group (a per-mapping loop that resolved only the first mapping's values was a real bug here, fixed 2026-09-12 — a second field sharing a lookup used to silently fail to resolve values that weren't also present under the first field's column). **`IngestionSourceConfig.DeleteNonSent`** (bool, default `false`, per-source in `ingestion.config.json`) opts a view into "full sync" semantics: after upserting, any existing active row not present in the current file gets soft-deleted (`deletedAt`/`deletedBy`, same as everywhere else — never a hard delete). For `Centers`/`Products` this scans the whole table (`Code`/`Reference` not in the sent set) since master data is small; for `CenterProducts`/`Forecast`/`History` the deletion candidates are scoped to only the `(IdProduct, IdCenter)` pairs already fetched for the upsert step (reusing that query, not a second full-table scan) — so turning this on for `Forecast`/`History` only prunes rows for the products/centers actually present in that file, not the entire fact table. Each writer's `IIngestionWriter.WriteAsync(mappedRows, deleteNonSent, ct)` takes the flag explicitly; `IngestionWriteResult.Deleted`/`IngestionRunResultDto.RowsDeleted` report the count. Safety net: `IngestionService` only calls the writer when `validRows.Count > 0`, so a source file that reads empty (misconfigured path, wrong header) can't accidentally wipe a whole table — but a file that's merely *incomplete* (truncated, missing some legitimate rows) will still delete those as "not sent," so `DeleteNonSent` is inherently riskier for `Forecast`/`History` than for master data; it defaults to `false` and should stay opt-in per source. **`IngestionSourceConfig.Key`** (list of target field names, e.g. `["Code"]` for `Centers`, `["Reference"]` for `Products`, `["IdProduct", "IdCenter"]` for `CenterProducts`, `["IdProduct", "IdCenter", "Date"]` for `Forecast`/`History`) declares which mapped fields are that view's join/match key — the fields used to find the existing row on insert-or-update, and which are *never* overwritten once a row exists (each writer's update branch simply never assigns to them, by construction — the same "immutable after creation" convention as `CenterProduct.IdProduct`/`IdCenter` etc. elsewhere in this doc, just for the ingestion pipeline instead of the CRUD API). `Key` is validated by `IngestionService.ValidateKeyMappings` before a run touches the DB: every declared key field must have a `FieldMappingConfig` targeting it, and that mapping can't be a constant (`Source: null`) — a join key with a fixed value would collapse every row onto the same match, which is always a config mistake, not an intended default. Add a field to `Key` whenever a new view's business/natural key should be protected this way; besides that validation, `Key` isn't read by the writers themselves (each writer already hardcodes its own matching logic in code, per the `Key` values listed above — keep the two in sync when either changes) — it **is** read by `FieldMappingEngine.MapRows`, though: every row-level error it produces is prefixed with `[SourceColumn=value, ...]` built from `Key`'s target fields resolved back to their `FieldMappingConfig.Source` CSV column names (e.g. `[MaterialCode=UNKNOWN, CenterCode=C1]`), so a failing row is identified by the values an operator can actually search for in the source file — not a line/row number (tried and explicitly rejected 2026-09-12: "não precisa ser o número da linha apenas as colunas key para identificar"). **Cron/scheduled triggering was explicitly deferred** (2026-09-12, "não precisa criar o cron agora") — today the pipeline only runs on-demand via `POST /api/robot/run`; when it's added, per [[project_robot_ddmrp_design]] use a simple daily-time `BackgroundService` (config-driven "run at HH:mm"), not a full cron-expression library, unless told otherwise. The exception-boundary convention holds here too: `Infra.Data` readers/writers/config-provider throw plain BCL exceptions (`FileNotFoundException`, `NotSupportedException`) for I/O/config problems — `IngestionService` (Application layer) is what catches those and re-throws as `BadRequestException`, since `Infra.Data` has no reference to `Service.Application` (only `Service.Domain`, same as every repository) and `AppException` lives in Application.
- **Calculation pipeline ("Robot" — DDMRP pre-calc half)**: `POST /api/calculation/run` (`[Authorize]`, no partial-step option — always every step) calls `CalculationService.RunAsync(ct)` directly; `RobotService` also calls it, as the second half of the composed run. It reads `Service.API/calculation.config.json` (path from `Calculation:ConfigPath`) via `JsonCalculationConfigProvider`, a flat ordered list of `CalculationStepConfig { Name, Parameters: [{ Name, Value }] }`. **Calculation steps are plain C# classes, not SQL Server stored procedures** — this was tried first (a generic `EXEC dbo.[Name]` executor calling DB-persisted procedures) and explicitly rejected (2026-09-12, "não gosto da ideia de procedures") specifically because deploying/changing one meant an EF migration just to run `CREATE OR ALTER PROCEDURE`. Instead, each step is an `ICalculationStep` (`Service.Domain/Interfaces/ICalculationStep.cs`: `CanHandle(string name)` + `ExecuteAsync(CalculationStepConfig, ct)`) implemented in `Service.Infra.Data/Calculation/Steps/*.cs`, constructor-injected with `ApplicationDbContext` — same `CanHandle`-dispatch shape as `IIngestionWriter`, registered the same way (`IEnumerable<ICalculationStep>` in DI, `CalculationService` picks the one whose `CanHandle(stepConfig.Name)` matches, throwing `BadRequestException` up front if none does — mirrors ingestion's "no writer/reader matches" handling). A step is free to implement its logic however fits — LINQ, `ExecuteUpdateAsync`, or (like `CalculateAduStep`) a hand-written set-based SQL string run via `ApplicationDbContext.Database.ExecuteSqlRawAsync` when the logic doesn't translate cleanly through LINQ — but there is **no DB-persisted object and no migration needed to change one**; editing the C# file *is* the deployment. `CalculationService.RunAsync` executes steps **strictly in config order** and **stops at the first failing step** (unlike ingestion's per-row tolerance) — DDMRP calculations are assumed to be a dependency chain (a later step may read what an earlier one wrote), so continuing past a failure risks computing on wrong data; a step's own exception handling should catch its failure and return `CalculationStepResult { Success = false, Error }` rather than let it throw (see `CalculateAduStep`'s try/catch) — steps after a failure are simply never attempted (not represented in the result list at all). **`Service.Infra.Data/Calculation/Steps/*.cs`** is the centralized home for every calculation step (`CalculateAduStep.cs` was the first, registered in `CanHandle` as `"CalculateAdu"`; `CalculateAdiStep.cs` is the second, `"CalculateAdi"`). **`Formulas.md`** (repo root) is the parallel centralized doc for the *business rule* each step implements — write or update the formula there before/alongside writing its step, not after. `calculation.config.json.example` now has both steps: `"CalculateAdu"` (empty `parameters` — its day-count inputs live on `CenterProduct.HistoryAduDays`/`FutureAduDays`, not pipeline parameters) and `"CalculateAdi"` (one parameter, `{ "name": "ThresholdDays", "value": "360" }`) — **`CalculateAdi` is the first step whose input is a step-level config parameter rather than a per-`CenterProduct` column**: `CalculateAdiStep` reads `step.Parameters` for `"ThresholdDays"` (case-insensitive, defaults to `360` if the parameter is omitted; returns `CalculationStepResult{Success=false}` — not a thrown exception — if present but not a valid int) and applies that single threshold to every `CenterProduct` in one run, unlike Adu's per-item `HistoryAduDays`/`FutureAduDays`. It also uses `ExecuteSqlInterpolatedAsync` instead of `ExecuteSqlRawAsync` specifically because the SQL now has a runtime-variable piece (the threshold) that needs to be a real SQL parameter, not string-concatenated — `ExecuteSqlRawAsync` stays correct for `CalculateAduStep` since that step's SQL has no external input to parameterize. **`CalculateAduStep` also writes `CenterProduct.StandardDeviation`/`Cv`** (2026-09-12, "ambas as regras usam praticamente os mesmos dados que o cálculo de ADU, então vamos colocar no mesmo step") — same `HistoryAduDays`/`RankedHistory` window as Historico (population `STDEVP`/`AVG` over `ISNULL(Quantity, 0)`, `Cv = StandardDeviation / Average` with `Cv = 0` when the average is `0`), independent of `FutureAduDays`/Misto. **Every calculation step that writes calculated columns runs a reset `UPDATE ... SET <column> = 0` first, before the real computation** (2026-09-12, "antes de realizar o calculo voce deve rodar um update Zerando as colunas de todos os itens (isso serve para todas as colunas calculadas)") — `CalculateAduStep` zeroes `Adu`/`StandardDeviation`/`Cv`, `CalculateAdiStep` zeroes `Adi`, both as the first statement in their SQL batch; the real `UPDATE` immediately after already covers every active row unconditionally, so the reset doesn't change the final result today, but it's the standing convention for every calculated `CenterProduct` column going forward — add it when writing a new one, even if it looks redundant against the current query shape. **`POST /api/robot/run` (`RobotService`) is the composed, "real" Robot trigger**: it calls `IIngestionService.RunAsync(view: null, ct)` (every configured ingestion source) and only then `ICalculationService.RunAsync(ct)`, returning both result sets in one `RobotRunResultDto { Ingestion, Calculation }` — **the data load always runs first, by construction** (calculation is a second, sequential `await`, not parallel), and if ingestion throws, calculation is never invoked at all (the exception propagates before that line runs). **History**: `IngestionController`/`CalculationController` were briefly removed (2026-09-12, "a única rota exposta deve ser run") in favor of `/api/robot/run` alone, then restored the same day — both standalone routes exist again for testing/debugging one half of the pipeline in isolation, alongside `/api/robot/run` for the guaranteed load-then-calculate production path. When cron triggering is eventually added (see the deferred note above), it should call `IRobotService.RunAsync` (not re-implement the ordering), same as the HTTP route does.
- **Database provider is SQL Server** (`Microsoft.EntityFrameworkCore.SqlServer`, wired via `options.UseSqlServer(...)` in `Service.Infra.Ioc/DependencyInjection.cs`) — the project ran on PostgreSQL/Npgsql until 2026-09-12, when it was switched to SQL Server only (not dual-provider; there is no runtime provider switch). `AuditableEntityConfigurationExtensions.ConfigureAuditFields` uses `HasDefaultValueSql("GETUTCDATE()")` (was `now()` under Npgsql) for `createdAt`'s DB-level default. All prior EF migrations (generated against Npgsql) were deleted since their SQL isn't valid against SQL Server — the very next step after this switch is generating a fresh initial migration (`dotnet ef migrations add InitialCreate --project Service.Infra.Data --startup-project Service.API`) against a real SQL Server instance, per [[feedback-migrations]] the user runs this themselves. `Service.API/.env.example`'s `ConnectionStrings__DefaultConnection` now shows the SQL Server format (`Server=...;Database=...;User Id=...;Password=...;TrustServerCertificate=True;`) instead of the old Npgsql one. Watch for `DateTime.Kind` differences if this ever needs to move providers again: Npgsql required UTC-kind `DateTime`s for `timestamptz`, SQL Server's `datetime2` is lenient about `Kind` — don't rely on that leniency, keep populating audit/date fields with `DateTime.UtcNow` regardless of provider.
