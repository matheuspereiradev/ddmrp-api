# TODO — Problemas técnicos e de segurança

Lista de achados do diagnóstico técnico do repositório, ordenados por severidade.

## Crítico

- [ ] **Pipeline de ingestão (Robot) não escala pra CSVs muito grandes (ex.: 1 milhão de linhas).** O cliente vai enviar arquivos com muitos itens — no design atual isso é um risco real de lentidão/estouro de memória/timeout, não só "podia ser mais rápido". Achados (discussão de 2026-09-13, nada implementado ainda):
  - `IngestionService.RunSourceAsync` (`Service.Application/Services/IngestionService.cs`) drena o `IAsyncEnumerable` do `CsvIngestionSourceReader` inteiro pra uma `List` e depois gera mais 2-3 listas do tamanho do arquivo (`mapped`, `validRows`, `errors`) — várias coleções de ~1M itens residentes em memória ao mesmo tempo, antes mesmo de tocar no banco.
  - Todo writer (`Service.Infra.Data/Ingestion/Writers/*.cs`) busca as linhas existentes via `.Contains()` sobre a lista de chaves distintas do lote — vira uma cláusula SQL `IN (...)` com potencialmente centenas de milhares de valores (risco de estourar limite prático/gerar plano de execução ruim). `DeleteNonSent` piora: usa `!Contains(...)`, que não usa índice direito e força varredura da tabela.
  - **`GenericTableIngestionWriter.FetchExistingGenericAsync` carrega a tabela alvo inteira (`Where(deletedAt == null).ToListAsync()`) em toda execução, sem escopar pelas chaves do lote** — hoje só afeta `CenterProducts` (via `Stock`), mas essa tabela é exatamente o tipo que pode crescer pra centenas de milhares/milhões de linhas num cliente grande.
  - Nenhum writer usa `AsNoTracking()`; nenhuma configuração de `ChangeTracker.QueryTrackingBehavior` no `ApplicationDbContext`. Todas as entidades (existentes + novas) ficam rastreadas pelo EF Core simultaneamente, e um único `SaveChangesAsync` no fim processa o lote inteiro numa transação só — `DetectChanges` degrada de forma não-linear com a quantidade de entidades rastreadas, e uma transação de milhões de linhas arrisca crescimento de log/timeout/lock longo.
  - Não existe chunking/paginação em nenhum ponto do pipeline (leitura → lookup → mapping → writer): é tudo um lote só, do início ao fim.
  - **Direção recomendada (não iniciada)**: mover os writers de "carregar como entidade EF + `SaveChangesAsync` único" para SQL set-based com `JOIN`, no mesmo espírito dos steps de cálculo (`CalculateAduStandardDesvAndCvStep`/`CalculateAdiStep`, que já usam SQL bruto por motivo de performance). Passo prático: `SqlBulkCopy` do lote validado (já convertido/tipado em C#, erro por linha continua sendo pego antes disso) pra uma tabela de staging, depois `UPDATE ... FROM target JOIN staging ON chave` / `INSERT ... SELECT ... LEFT JOIN target ON chave WHERE target IS NULL` / (se `DeleteNonSent`) `UPDATE target SET deletedAt=... FROM target LEFT JOIN staging ON chave WHERE staging IS NULL`. Isso elimina o `IN` gigante, a carga da tabela inteira do `GenericTableIngestionWriter`, e o overhead de tracking do EF — mas é uma mudança de arquitetura nos 7 writers (ou um helper compartilhado), não um ajuste pontual; tratar como tarefa própria quando for priorizada.

- [ ] **`ExecutionBuffer` (relatório `GET /api/report/openOrders`) calcula errado quando uma ordem de `Id` menor tem `DeliveryDate` maior que uma de `Id` maior.** Levantado 2026-09-14 pelo usuário. A fórmula (ver `Formulas.md`) soma `PendingQuantity` das "ordens anteriores" filtrando por duas condições **independentes**: `Id < id da ordem atual` **e** `DeliveryDate <= DeliveryDate da ordem atual` — não uma única chave de ordenação. Se a ordem A (`Id=1`) tem `DeliveryDate` 20/09 e a ordem B (`Id=2`, mesmo produto+centro) tem `DeliveryDate` 10/09 (criada depois mas entrega antes), o `ExecutionBuffer` de B não inclui A (`A.DeliveryDate > B.DeliveryDate`), mas o de uma ordem C (`Id=3`, `DeliveryDate` 25/09) inclui tanto A quanto B — mesmo que a sequência real de execução (por data de entrega) seja B antes de A. Usar `Id` como proxy de "ordem cronológica de criação" só bate com a sequência de entrega se ids crescentes sempre corresponderem a `DeliveryDate`s crescentes, o que não é garantido (nada impede cadastrar uma ordem com entrega mais cedo depois de uma com entrega mais tarde). Precisa decidir se a comparação correta é só por `DeliveryDate` (ignorando `Id`, com algum critério de desempate pra entregas na mesma data), só por `Id`, ou a combinação atual mesmo — não mexer na fórmula sem confirmar, foi implementada exatamente como pedida.
- [ ] **Trocar `Task<ActionResult>` por `Task<ActionResult<T>>` em todas as actions dos controllers.** Levantado 2026-09-14 ao implementar `ApiResponseWrapperOperationFilter` (ver `CLAUDE.md`) — hoje toda action de todo controller retorna `ActionResult` sem tipo genérico, então o `ApiExplorer` do ASP.NET Core não tem informação de tipo pra reportar ao Swagger, e o filtro cai no fallback `ApiResponseDto<object>` (envelope certo, mas `data` sem shape). Trocar pra `ActionResult<T>` é mudança de assinatura apenas — `return Ok(dto)`/`return NotFound()` etc. continuam compilando igual via conversão implícita, sem mudar comportamento — mas é mecânica e grande: ~86 actions em 22 controllers. Escopo próprio, não feito junto com o filtro.
- [ ] **Adicionar funcionalidade de calendário não produtivo.** Levantado 2026-09-14, escopo ainda não definido. Hoje nenhum cálculo do Robot (Adu, Adi, LeadTime, `CoverageDays`, horizonte de `QualifiedDemand`, etc.) considera dias não produtivos (feriados, paradas de fábrica, fins de semana quando não úteis) — todo cálculo de dias corridos assume calendário cheio. Falta detalhar: granularidade (global, por `Center`, por `Product`?), se é uma tabela de datas específicas ou uma regra recorrente (dia da semana + exceções), e quais cálculos passam a descontar esses dias (`HistoryAduDays`/`FutureAduDays`, `LeadTime`, o horizonte de spike). Perguntar antes de implementar.
- [ ] **`CalculateNormalBufferZonesStep`/`CalculateMinMaxBufferZonesStep`/`CalculateDynamicMinMaxBufferZonesStep`/`ApplyZafStep` ainda não tratam MTO (Make-to-Order).** Implementados 2026-09-13 (`Service.Infra.Data/Calculation/Steps/*.cs`, ver `Formulas.md`), mas nenhum considera se o item é MTO — itens MTO (`BufferProfile.IsMakeToOrder = true`, ou o futuro flag `CenterProduct.IsMto` calculado pelo step `SetMto`, ver [[project_setmto_step_design]], ainda não implementado) precisam de tratamento próprio no cálculo de zonas, que ainda não foi definido. Hoje um item MTO cai no mesmo cálculo de um item não-MTO (já que `BufferType` e `IsMto`/`IsMakeToOrder` são conceitos independentes), o que provavelmente está errado.
- [ ] **Autorização por permissão, não por papel fixo.** Cada rota de controller deve declarar qual **permissão** ela exige, e a checagem deve verificar se o **perfil (`Role`) do usuário** tem essa permissão — configurável em runtime pelo usuário (perfil "Gerente" tem X permissões, "Vendedor" tem Y), não hardcoded em `[Authorize(Roles = "Admin")]`. O `new Claim(ClaimTypes.Role, role)` comentado em `AuthenticateProvider.GenerateToken` é o modelo antigo/errado — não descomentar, é RBAC simples demais pro que se quer aqui.
  - **Modelo de dados necessário**: entidade `Permission` (catálogo de permissões, ex.: `users.create`, `roles.manage`) + `RolePermission` (junção N:N entre `Role`, que já existe, e `Permission`), com endpoints pra administrar essa associação.
  - **Como o controller declara a permissão exigida**: usar policy-based authorization do ASP.NET Core (`[Authorize(Policy = "users.create")]` ou um atributo customizado tipo `[RequirePermission("users.create")]`), nunca `Roles =`.
  - **Onde a checagem acontece — decisão em aberto**: (a) permissões resolvidas no login e embutidas como claims no JWT (rápido, sem consulta ao banco por request, mas fica desatualizado até o access token expirar/renovar se um admin mudar as permissões do perfil dele — agora que o refresh token existe, isso significa "até o próximo refresh", que pode ser configurado para um intervalo curto); ou (b) checagem no banco a cada requisição via `IAuthorizationHandler` customizado, com cache (efeito imediato quando a config muda, custa uma consulta a mais, mitigável com cache). Como a ideia é o usuário reconfigurar isso em runtime, opção (b) com cache tende a fazer mais sentido.
